---
name: review:diff
description: 指定されたコミットやブランチとの差分をレビュー
argument-hint: [branch/tag/commit] [--target <絞り込み指定>] [--simple] [--cross] [--report]
model: sonnet
---

このスキルではレビューを行い、レビュー結果をまとめたり、実装計画書を作成したりすることに集中する
**このスキルの実行ではファイルの修正を行ってはならない**

## 引数

$ARGUMENTS を次の5項目に解析する。

- **diff 対象**（省略可）: 最初のフラグ以外の引数。branch/tag/commit を指定する。省略時はタスク 1. の「diff モードの決定」に従って自動決定する
- **`--target <絞り込み指定>`**（省略可）: レビュー対象ファイルを絞り込む自然言語の指定。`--target` の直後から次のフラグまたは末尾までを値として扱う（例: 「新規ファイルのみ」「既存ファイルのみ」「認証に関係するファイルのみ」「`src/api/` 以下」）
- **`--simple`**（省略可）: 簡易レビューモードを有効化する
- **`--cross`**（省略可）: ファイルをまたぐ同根の指摘をまとめる機能。デフォルトでは無効にする
- **`--report`**（省略可）: レビュー結果を md 報告書として書き出す。デフォルトでは書き出さない。指摘の正本は reviewview にあり、md は求められたときだけ生成する派生物のため

## コンテキスト

- 渡された引数: $ARGUMENTS

## タスク

1. 引数を解析し、diff 対象・絞り込み指定・簡易モードの有無を確定し、**diff モード** を決定する
   - diff 対象が指定されている場合 → **コミット比較モード**（指定された branch/tag/commit を diff 対象とする）
   - diff 対象が未指定の場合、以下を上から順に判定して最初に該当したモードを使う:
     1. `git diff --cached --name-status` の出力が空でない → **staged モード**（stage された内容のみをレビューする）
     2. `git diff --name-status` の出力が空でない → **worktree モード**（未コミットの変更を全てレビューする。stage が空なので作業ツリーの差分が未コミット変更の全てと一致する）
     3. どちらも空 → **merge-base モード**: デフォルトブランチ（`git symbolic-ref --short refs/remotes/origin/HEAD` で解決し、失敗時は `main`、それも実在しなければ `master`）と現在のブランチのマージベースを `git merge-base HEAD <デフォルトブランチ>` で求め、その SHA を diff 対象とする（以降はコミット比較モードとして扱う）
   - 未追跡（untracked）ファイルはどのモードでも判定・レビュー対象に含めない
2. レビュー対象ファイル一覧を取得する（A=新規 / M=既存変更 などのステータスは絞り込み判定に使う）
   - 先に **BASE ハッシュ** と **HEAD ハッシュ** をフル SHA で解決し、Step 8 の `@review-consolidator` 起動まで保持する
     - コミット比較モード: `git rev-parse <diff対象>` の結果を `base_commit`、`git rev-parse HEAD` の結果を `head_commit` として保持
     - staged / worktree モード: `git rev-parse HEAD` の結果を `base_commit` と `head_commit` の両方として保持
     - どちらも短縮せずフル 40 桁の SHA-1 を使う
   - コミット比較モード: `git diff --name-status <base_commit> <head_commit>` を実行する
     - 7. の差分書き出しと基準を揃え、作業ツリーだけに差分があるファイルを混ぜないため
   - staged / worktree モード: Step 1 の判定で実行した `git diff --cached --name-status` / `git diff --name-status` の出力をそのまま使う
   - **リネーム表記の正規化**: ステータスが `R` で始まる行は、タブ区切りの 3 列目（新パス）をレビュー対象パスとして使う（2 列目は旧パス）。以降のすべての手順（絞り込み判定・差分取得・`@review-consolidator` へ渡す対象ファイル一覧）で正規化後の新パスを使う
3. 絞り込み指定がある場合、ステータス・ファイルパス・必要に応じて差分内容から該当性を判断し、ファイル一覧を絞り込む
4. レビュー対象ファイル一覧（絞り込み後）が空の場合はその旨をユーザーに通知し終了
5. **レビュー対象をバッチにまとめ、「バッチ × レビュー観点」の組み合わせごとに1つのサブエージェントを並列に起動する**
  - 5-1. **各ファイルの差分行数を取得する**
    - 各ファイルの (insertions + deletions) の合計行数を、次のコマンドを **1 回だけ** 実行して取得する
      - コミット比較モード: `git diff --numstat <base_commit> <head_commit> -- <レビュー対象ファイル（絞り込み後）...>`
      - staged モード: `git diff --cached --numstat -- <...>`
      - worktree モード: `git diff --numstat -- <...>`
    - **リネーム表記の正規化**: パスに `=>` を含む行は新パス側を取り出して使う。中括弧形式 `dir/{old.ts => new.ts}` は `dir/new.ts` に、中括弧なしの `old => new` 形式は `=>` の右側を使う。リネーム表記のままでは `git diff -- <filepath>` に渡せないため
  - 5-2. **観点グループに分ける**
    - **テストファイルの判定**: 以下のいずれかに当てはまるものをテストファイルとして扱う。パスを `/` で区切ったセグメント単位で判定する（プロダクションコードの `testUtil.ts` や `latest/` のような名前を誤って拾わないため）
      - ファイル名に `.test.` または `.spec.` を含む
      - パスに `__tests__/` または `__mocks__/` のディレクトリセグメントを含む
      - リポジトリルート直下の `test/` または `tests/` ディレクトリ配下にある
      - テスト用のフィクスチャ・モック・セットアップユーティリティなど、上記の形式的判定では迷うファイルはテストファイル群に含める（テスト資材のレビューは @reviewer-for-test-code が担当するため）
    - テストファイル群 → 以下の1観点のみ
      - @reviewer-for-test-code
    - 非テストファイル群 → 通常モードは以下の3観点、`--simple` 指定時は @reviewer-for-security-performance を除いた2観点
      - @reviewer-for-logic（実装の正当性・エッジケース・例外処理）
      - @reviewer-for-design（DRY/KISS/SOLID/YAGNI・責務分離・依存関係制約）
      - @reviewer-for-security-performance（セキュリティ・パフォーマンス）
  - 5-3. **各グループ内でバッチを組む**
    - ファイルをパス順（辞書順）に並べる。近いディレクトリのファイルが同じバッチに入り、レビュー時の文脈が繋がるため
    - 単体で **200 行以上** のファイルは、それだけで1バッチにする（単独バッチ）
    - それ以外のファイルは、先頭から順に **合計 200 行以内かつ最大 5 ファイル** まで詰めて1バッチにする。どちらかの上限に達したらそこでバッチを切り、次のバッチを開始する
    - 非テストの各観点は**同一のバッチ構成を共有する**（バッチを観点ごとに組み直さない）
    - 各タスクは「1つのバッチ（1〜5ファイルの差分）を、1つの観点専門のサブエージェントでレビューする」単位
    - バッチ予算 200 行 / 最大 5 ファイルは、実差分での試算に基づく値
  - 5-4. **起動前にタスク数を見積もる**
    - `printenv CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` を 1 回だけ実行し、同時実行数の上限を決める。正の整数が返ればそれを上限とし、空または正の整数以外なら 20 とする。この上限は 8. の起動制御でもそのまま使う
    - 上限が、どれか 1 バッチの消費枠（8-2.）より小さい場合は、その旨をユーザーに伝えて終了する。そのバッチは 8-3. でいつまでも起動できないため。上限を上げるか、`--simple` で消費枠が収まるなら指定し直すよう案内する
    - 見積もりタスク数 = 非テストバッチ数 × 観点数 + テストバッチ数 + 総バッチ数
    - 総バッチ数を加算する理由: レビュアーは `@review-consolidator` にネスト起動されメインの画面から見えなくなるが、起動数としてのコスト警告を維持するため。この式は 8-2. の消費枠を全バッチ分合計した値と一致する
    - **見積もりタスク数が上限を超える場合のみ** AskUserQuestion ツールでユーザーに確認する。選択肢は次の3つ
      - (a) そのまま起動する
      - (b) `--simple` 相当の観点数に縮退して再度見積もる
      - (c) 中止して `--target` で対象を絞り直す
    - 確認の前に、見積もりタスク数と、起動を分ける回数の最小値（見積もりタスク数 ÷ 上限 の切り上げ）をテキストで伝える。バッチは消費枠の単位でしか起動できず上限いっぱいに詰まらないことがあるため、実際の回数はこれより多くなりうると添える。上限を超えた分は 8. で完了を待ってから起動するため、回数に比例して所要時間が延びる
    - 上限を確認の基準にするのは、1 回で起動しきれるかどうかが所要時間の大きな分かれ目であり、上限の変更にも追随できるため
    - (b) を選んだ結果、再見積もりでも上限を超える場合は同じ選択肢で再度確認する
    - 上限以下の場合は確認せずそのまま起動する（通常のレビューで不要な問いかけを出さないため）
6. reviewview にレビューを作る
   - `start_review` を `findings` なしで呼び、`reviewId` を受け取る。この時点で diff が凍結される
   - コミット比較モードと merge-base モードでは、2. で解決した `base_commit` を `base` に、`head_commit` を `head` に渡す
   - staged モードでは、2. で解決した `base_commit` を `base` に、予約値 `'index'` を `head` に渡す
     - `'index'` はステージ済みの内容（`git diff --cached` 相当）を凍結させる予約値。Step 7 の diff ファイルも `git diff --cached` から作るため、統合エージェントの行番号の基準と一致する
     - 省略すると作業ツリーの未コミット変更（`HEAD..worktree`）が凍結され、未ステージの変更があるとステージ済み差分と食い違う
   - worktree モードは `base` と `head` を省略してデフォルトに任せる。省略時のデフォルトは `base` が HEAD、`head` が作業ツリーの未コミット変更である
   - 凍結される diff が統合エージェントの行番号の基準とずれると、アンカーが無関係な行に着くか isOrphaned で返る
   - `cwd` には `git rev-parse --show-toplevel` の結果（絶対パス）を渡す
     - MCP サーバの `--cwd` に依存せず、レビュー対象のリポジトリを明示するため
     - 渡さないと MCP サーバ起動時の `--cwd` が使われ、別のリポジトリの diff が凍結され得る
7. バッチごとの diff と関連ファイル一覧をファイルへ書き出す
   - タイムスタンプは `bun run "${CLAUDE_PLUGIN_ROOT}/skills/document-saver/scripts/get-timestamp.ts"` で取得し全バッチに使う
   - 取得したら `mkdir -p "$TMPDIR/review-diff-<timestamp>"` を 1 回だけ実行する。リダイレクトは親ディレクトリを作らないため
   - 差分を取得するコマンドはモード別に次のとおりで、5. までの判定結果をそのまま使う。末尾のリダイレクトは省略できない

     ```sh
     # コミット比較モード
     git diff <base_commit> <head_commit> -- <filepath1> <filepath2> ... > "$TMPDIR/review-diff-<timestamp>/diff-<NN>.diff"

     # staged モード
     git diff --cached -- <filepath1> <filepath2> ... > "$TMPDIR/review-diff-<timestamp>/diff-<NN>.diff"

     # worktree モード
     git diff -- <filepath1> <filepath2> ... > "$TMPDIR/review-diff-<timestamp>/diff-<NN>.diff"
     ```

   - 標準出力で受け取るとメインセッションのコンテキストに差分本文が乗るため、必ずファイルへリダイレクトする
   - コミット比較モードで作業ツリーの差分ではなくコミット間の差分を使うのは、行番号の基準を統一するため
   - `<NN>` は非テストバッチ群、テストバッチ群の順に全バッチを通して 01 から振る。番号が衝突するとファイルが上書きされ静かに壊れる
   - 続けてバッチごとに、**変更ファイルを import している側（逆依存）の一覧** を同じディレクトリへ書き出す
     - まずそのバッチの対象ファイルのパスを 1 行 1 件で `$TMPDIR/review-diff-<timestamp>/files-<NN>.txt` に書き出す。パスはレビュー対象プロジェクトのルートからの相対パスで、2. で正規化した表記をそのまま使う
     - 次のコマンドをバッチごとに実行する

       ```sh
       bun run "${CLAUDE_SKILL_DIR}/scripts/find-reverse-deps.ts" --root <レビュー対象プロジェクトのルート絶対パス> --files "$TMPDIR/review-diff-<timestamp>/files-<NN>.txt" --out "$TMPDIR/review-diff-<timestamp>/related-<NN>.txt" --limit 10
       ```

     - `--root` には Nuxt プロジェクトのルート（`pages/` や `composables/` を持つディレクトリ）の絶対パスを渡す。多くの場合はリポジトリルートと一致する。`--files` にはそのバッチの対象ファイル一覧を渡す
     - 出力は key=value の行指向形式。変更ファイル 1 件につき 1 ブロックで空行区切り、キーは `target` / `domain` / `related` / `omitted` / `autoimport`
     - `--limit 10` の根拠: 実作業の非テスト実装ファイル 112 件の実測で p50=2 / p75=3 / p90=8 だった。10 件超は 8.0% にとどまり、分布の切れ目が 10〜16 の間にある
     - スクリプトが `error=` から始まる行を返した場合は、その旨をユーザーに伝えたうえで関連ファイル一覧なしでレビューを続行する。逆依存は補助情報であり、欠けてもレビュー自体は成立するため
     - `related-<NN>.txt` の中身はメインセッションで Read してはならない。差分ファイルと同じく、読むのはレビュアーだけ
8. `@review-consolidator` を**サブエージェントとして**、同時実行数の上限に収まる分ずつバッチ数だけ起動する
   - `Agent` ツールに `name` を渡してはならない。`name` を付けるとチームメイトとして起動され、ネスト起動したレビュアーの `SubagentHandback` が到達判定の型チェックで常に失敗する。指摘が統合エージェントへ届かず、reviewview へ未投入のまま止まるため
   - 各インスタンスへ次の7項目を渡す
     - バッチ番号
     - そのバッチの diff ファイルの絶対パス
     - そのバッチの関連ファイル一覧ファイル（`related-<NN>.txt`）の絶対パス。7. で生成できなかった場合は「なし」と明示して渡す
     - そのバッチの対象ファイル一覧
     - 起動するレビュアー名。5-2. の `@reviewer-for-*` ではなく、プラグイン接頭辞付きのエージェント種別で渡す
       - `cbo:reviewer-for-logic` / `cbo:reviewer-for-design` / `cbo:reviewer-for-security-performance` / `cbo:reviewer-for-test-code`
       - 統合エージェントはこの値をそのまま `Agent` ツールの `subagent_type` に使う。プラグインのエージェントを接頭辞なしで起動しようとすると失敗するため
     - 6. で受け取った `reviewId`
     - 2. で解決した BASE・HEAD のフル SHA
   - 割り当てる観点は 5. の判定結果をそのまま使う
   - `Agent` ツールに `model` を渡さず、レビュアーのモデルも入力に含めない。統合エージェント・レビュアーとも、各エージェントのフロントマターの設定を使わせる
   - 8-1. **同時実行数の上限を守る**
     - 上限は 5-4. で決めた値を使い、`printenv` を再実行しない
     - 上限を守るのは、上限に達すると `Agent` ツールは待機せず即座に失敗し、統合エージェントがネスト起動したレビュアーも同じ枠を消費するため。全バッチを一度に起動すると、起動できないバッチや、レビュアーを起動できず 0 件のまま終わるバッチが出てレビューが静かに欠ける
   - 8-2. **バッチごとの消費枠を数える**
     - 消費枠 = 統合エージェントの 1 + そのバッチに割り当てたレビュアー数
     - 通常モードの非テストバッチは 4、`--simple` 指定時の非テストバッチは 3、テストバッチは 2 になる
   - 8-3. **枠に収まる分だけ起動する**
     - 未起動のバッチをバッチ番号順に取り出し、実行中の統合エージェントの消費枠の合計が上限を超えない範囲で起動する
     - 同じ回に起動するインスタンスは互いに依存させず並列に起動する
     - 枠の空きを待つのはメインセッションだけが担う。統合エージェントには自分の子の完了通知しか届かず、他の枠の解放を知れないため。枠を握ったまま待たせると、互いの解放を待ち合って止まる
   - 8-4. **完了通知を受けるたびに残りを起動する**
     - 統合エージェントの完了通知が届いたら、その消費枠が空いたものとして、残りのバッチを 8-3. と同じ条件で起動する
     - 待機は完了通知を待つことで行い、ポーリングや sleep はしない
     - 未起動のバッチが無くなり、起動した全インスタンスが完了するまで繰り返す
   - 8-5. **起動に失敗したバッチを後で起動し直す**
     - メインセッションからの起動が `Concurrent subagent limit reached` で失敗したら、そのバッチを未起動に戻し、次の完了通知の後に起動し直す。このセッションの他のサブエージェントが枠を使っていると、消費枠の計算どおりでも上限に達するため
     - エラーメッセージには「Do not retry」とあるが、この再起動は行ってよい。枠が解放された後にだけ起動し直すので、同じ失敗を即座に繰り返すことにはならないため
   - 8-6. **起動できなかったレビュアーを補う**
     - 統合エージェントが `起動失敗のため未実行:` にレビュアー名を返した場合、そのバッチを未起動のバッチとして 8-3. の対象に戻す
     - 渡す7項目は元と同じ値を使い、レビュアー名だけを起動に失敗したものへ絞る。レビュアー名は返された `cbo:` 接頭辞付きの表記のまま渡す。消費枠も絞った後のレビュアー数で数える
     - バッチ番号には `03r1` のように再起動の回数を付けて渡す。reviewview の `ref` はレビュー全体で一意でなければならず、元の番号のままでは初回の統合エージェントが投入した `ref` と衝突するため
     - 指摘は同じ `reviewId` へ投入される。起動に失敗したレビュアーだけを実行し直すので、指摘は重複しない
   - 8-7. **起動し直しを打ち切る条件**
     - 8-5. の失敗が、他に実行中の統合エージェントが無い状態で起きた場合は、起動し直さずに打ち切る。このスキルの外で枠が埋まっており、待っても解放を知らせる完了通知が届かないため
     - 8-6. の起動し直しは 1 バッチにつき 3 回（`r3`）までとし、それでも起動失敗が返ったら打ち切る。スキルの外で枠が埋まり続けていると、起動し直すたびに同じ失敗が返り際限なく続くため
     - 打ち切った場合は、未レビューのまま残ったバッチ番号とレビュアー名を 11. でユーザーに伝える
9. `--cross` が指定されている場合のみ `@review-cross-consolidator` を1件だけ起動する
   - 渡す入力は `reviewId` だけ
   - 8. の全インスタンス（8-5. と 8-6. で起動し直したものを含む）が完了してから起動する
10. `--report` が指定されている場合のみ `export_review` で md 報告書を生成させる
    - 8.（`--cross` 指定時は 9.）の全インスタンスが完了してから呼ぶ。8. では 8-5. と 8-6. で起動し直したものも含む。投入前に呼ぶと空の報告書になる
    - 引数は `reviewId` に 6. の `reviewId`、`outputDir` に `!`echo $MGZL_DIR`/reviews/<reviewId>/` を渡す。`includeTriage` は渡さない（この時点でトリアージは付いていない）
    - `outputDir` にレビューごとの専用ディレクトリを切るのは、`export_review` が出力先直下の `*.md` を毎回すべて削除してから書き直すため。`reviews/` 直下を渡すと過去の報告書が消える
    - 戻り値は `{ outputDir, indexPath, fileCount, findingCount, orphanCount }` のみで本文は返らない。保存先として `indexPath` と `outputDir` を控える
    - 報告書は生成時点のスナップショット。トリアージ後の判定込みで読みたい場合は同じ `outputDir` に `includeTriage: true` で再生成できる
11. `request_triage` を呼んでからユーザーへ通知して終了する
    - `request_triage` に 6. の `reviewId` を渡す
    - ユーザーへ伝える内容は次のとおり
      - `request_triage` が返したレビューの URL
      - 重要度（`[3]` / `[2]` / `[1]`）ごとの指摘件数の内訳。8. の各 `@review-consolidator` が返した件数を、起動し直したインスタンスの分も含めて合算する
      - 位置不明のため未投入の件数と isOrphaned の件数（統合エージェントが返した場合のみ）
      - 8-7. で打ち切った場合は、未レビューのバッチ番号とレビュアー名。指摘 0 件と区別できるよう、レビューされていないことを明示する
      - `--report` 指定時は md 報告書の保存先。10. の戻り値の `indexPath` と `outputDir` をそのまま伝える
      - `--report` 未指定時は、報告書が必要なら今回の `reviewId` を `export_review` に渡せば後から生成できること（レビューをやり直す必要はない）
      - トリアージを終えたら `reviewview-collect` で取り込めること

## メインセッションのコンテキストに関する制約

このスキルのフローは、差分本文・関連ファイル一覧・指摘本文・報告書本文のいずれもメインセッションのコンテキストを通さない前提で設計されている。次を守ること。

- 差分ファイル（`diff-<NN>.diff`）をメインセッションで Read してはならない
- 差分を取得するコマンドは必ずファイルへリダイレクトする。標準出力で受け取ってはならない
- 関連ファイル一覧（`related-<NN>.txt`）をメインセッションで Read してはならない。逆依存抽出スクリプトは `--out` で必ずファイルへ書き出させ、標準出力の `out=` 行だけを見る
- 生成された md 報告書（`index.md` とファイルごとの md）をメインセッションで Read してはならない
- 報告書の保存先パスは `export_review` の戻り値から取る。ディレクトリを走査して探してはならない
- ユーザーへの通知は、統合エージェントが返した件数と `request_triage` の戻り値（`--report` 指定時は `export_review` の戻り値も）だけで組み立てる
