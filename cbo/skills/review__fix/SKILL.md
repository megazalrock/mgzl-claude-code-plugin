---
name: review:fix
description: reviewview の finding id で指定された指摘を修正する。対象の選定は行わず、渡された id のみを修正して report_fix で報告する
argument-hint: [f-xxxxxxxx ...] [-y で確認をスキップ]
---

## コンテキスト
- 引数: $ARGUMENTS
- 引数の解釈ルール（上から順に判定する）
  - `f-` から始まるトークン → 修正対象の finding id（複数可、`f-xxxxxxxx` 形式）
  - `-y` フラグ → 実行確認をスキップ

## タスク

1. 対象の finding id を確定する
  - 引数から `f-` 形式のトークンを finding id として収集する
  - 引数の finding id が 0 件の場合、ユーザーに確認して処理を停止する（対象の選定はこのスキルの責務ではない）

2. 各 finding の内容を取得する
  - finding id ごとに `get_finding` を呼び、summary・rationale・suggestions・anchor・`triage`・`decidedAt` を取得する
  - `decidedAt` が null の指摘には着手しない。人間がトリアージを確定していない旨をユーザーへ伝え、その id を対象から外す
  - `triage` が「対応しない」「スコープ外」「偽陽性」のいずれかなら修正しない。反論もしない。判定をユーザーへ伝え、その id を対象から外す
  - `triage` が「要検証」の指摘は**検証対象**として保持する。この段階で検証と `report_fix` は行わない
  - `triage` が「修正する」の指摘は**修正対象**として保持する
  - 実行確認（3.）を経たうえで、検証対象を 4. で、修正対象を 5. で扱う
  - `triageReason` が付いている場合は、人間が書いた対応方針の指示として保持する

3. 実行確認を行う
  - `-y` フラグが引数にある場合は確認をスキップする
  - 無い場合は、修正対象と検証対象を区別して一覧を提示し、AskUserQuestion で実行してよいか確認する
    - 「修正: {id} {summary}」「検証: {id} {summary}」のように、対象の区分が分かる形で並べる
    - 選択肢は必ず「実行する」「実行しない」の順で並べる
  - 「実行しない」が選ばれた場合は、修正と検証のどちらも行わずに処理を終了する

4. 検証対象の指摘を検証する
  - 検証は `@code-investigator` サブエージェントに委任する。指摘 1 件につき 1 インスタンスを起動し、全件を並列に起動してよい
  - 5. の修正と並行して起動してもよい
  - `triageReason` は検証してほしい観点の指示として読む

  サブエージェントには次のような構造のプロンプトを渡す。

  ```
  reviewview の指摘 {finding id} が妥当かを検証してください。

  ## 指摘内容
  - summary: {summary}
  - rationale: {rationale}
  - suggestions: {suggestions}
  - anchor: {anchor}

  ## 人間が検証してほしい観点（triageReason より）  <!-- triageReason が非 null の指摘に限り挿入 -->
  {triageReason の文字列をそのまま貼り付ける}。

  この観点を最優先で扱ってください。

  ## 注意
  - コードは変更しない
  - 指摘が妥当か、根拠となるファイルと行を示して結論を返す。判断できない点は未解決として返す
  ```

  - 各インスタンスの結果が返り次第、本スキルが `report_fix` を `outcome: verified` で呼ぶ
    - `message` にはサブエージェントが返した結論と根拠を要約して書く
  - 妥当だと分かっても修正はしない

5. 修正対象の指摘を把握し、並列に修正する
  - `triageReason` に技術的な理由で従えない指摘は修正せず、`report_fix` を `outcome: blocked` で呼ぶ。`message` に理由を書いて、この指摘を以降の対象から除く
  - `suggestions` が 2 件以上あり `triageReason` がない指摘は、`-y` の有無にかかわらず AskUserQuestion で採用する提案を確認する
    - 選択肢には `suggestions` の各要素を提示する
    - ユーザーが採用案を選ばなかった場合は、その指摘を「採用案未指定によりスキップ」として対象から外し、最終レポートに載せる
  - 選んだ提案は、以降その指摘の `triageReason` として扱う
  - **各指摘について、起動する実装エージェント種別を判定する**（起動するのは 1 指摘につき 1 種類、集合ではない）
    - **修正対象がテストコードの場合**: `@test-implementer`
    - **それ以外の場合**: `@code-implementer`
    - **「修正対象がテストコード」の判定基準**: `anchor` が指すファイルが `*.test.ts` / `*.spec.ts` / `__tests__/` 配下のテストファイルのみである場合
    - 判定が曖昧な場合は `@code-implementer` を選択する（本体コードにも及ぶ指摘を安全側で扱えるため）
  - 対象の指摘は依存関係なく全件並列実行可能なため、判定結果に応じて `@test-implementer` または `@code-implementer` サブエージェントを **指摘単位で並列に起動** して修正する（判定は指摘単位で個別に行うため、同一並列バッチ内で両種が混在してよい）

  サブエージェントに渡すプロンプトは以下の構造で統一する（`@code-implementer` / `@test-implementer` どちらの場合も本文は共通）:

  ```
  reviewview の指摘 {finding id} を修正してください。

  ## 指摘内容
  - summary: {summary}
  - rationale: {rationale}
  - suggestions: {suggestions}
  - anchor: {anchor}

  ## 人間からの対応方針（triageReason より）  <!-- triageReason が非 null の指摘に限り挿入 -->
  {triageReason の文字列をそのまま貼り付ける}。

  この指示を最優先で解釈してください。`suggestions` の内容と食い違う場合は、こちらの指示を優先します。

  ## 注意
  - 修正対象は本指摘 1 件のみ。ほかの指摘には触れない
  - 修正完了後、担当エージェントの通常の報告形式で結果を返す
  ```

  - `triageReason` が `null` の指摘は、上記「人間からの対応方針」ブロックを付けない（`suggestions` をそのまま実装させる）
  - 各サブエージェントの修正が完了し次第、ただちに `report_fix` を `outcome: fixed`（デフォルト）で呼ぶ。全件の完了を待ってからまとめて呼ばない
    - 修正した側が結果を知っているため、この呼び出しは呼び出し元ではなく本スキルが担う
    - `message` には何をどう対応したかを書く
  - すべての指摘の修正・報告が完了してから次へ進む

6. 全指摘の修正完了後、コードレビューする
  - このループで検出した指摘は実装時点の自己検証であり、reviewview へ投入しない。`impl:execute` が自身の修正を検証する扱いと同じである
  - **次回起動するレビュアー集合**（次のラウンドで並列起動するサブエージェントの種類の集合。レビュー対象のファイルではなくサブエージェント種別のリスト）を初期化する
    - 修正対象がテストコードの場合: `@reviewer-for-test-code`, `@reviewer-for-comments`
    - それ以外: `@reviewer-for-logic`, `@reviewer-for-design`, `@reviewer-for-security-performance`, `@reviewer-for-comments`
  - 修正回数カウンタを 0 で初期化し、以下のレビュー→修正ループを実行する（修正は最大 2 回まで）
    1. **レビュー実施**
       - 「次回起動するレビュアー集合」に含まれるサブエージェントを**並列**で起動してレビュー
       - 各レビュアーには、修正した anchor のファイル群に限定した `git diff HEAD -- <files>` の unified diff 本文をプロンプトに含めて渡す。ラウンド 2 以降も同じ範囲で取り直す
         - レビュアーはシェル・git を持たず自力で差分を取得できないため、ファイルパス・diff の範囲指定だけでは対象として不十分
         - reviewview の finding からは元レビューの base を取得できないため、HEAD を基準とする
         - 元の変更が未コミットの場合はその分も差分に含まれるが、累積差分として扱う点は `impl:execute` と同じ
       - 2 ラウンド目以降は、差分に加えて前ラウンドの指摘記録を `## 前ラウンドの指摘と対処` ブロックとしてプロンプトに含めて渡す
         - 各レビュアー種別へ渡すのは、そのレビュアー種別が出した指摘のみ（「次回起動するレビュアー集合」で既に絞られている）
         - 書式は以下に厳密に従う（1 指摘につき 1 ブロック）

           ```
           ## 前ラウンドの指摘と対処
           ### R001 [2]
           位置: <path:line(s)>
           問題: <指摘内容>
           提案: <前回の提案>
           対処: 修正 | 削除 | 見送り
           対処内容: <変更内容、または見送った理由>
           ```

         - レビュアーは `## 前回指摘の再検証` 節で R-ID ごとに 解消 / 見送り容認 / 未解消 / 修正により新たな問題 を返し、`[3]`/`[2]`/`[1]` の各節には新規の指摘のみを挙げる
       - ラウンド 1 ではこのブロックを渡さない
    2. **判定**
       - ラウンド 1
         - `[2]` 推奨以上（`[2]`/`[3]`）の指摘が **0 件** → ループを抜ける
         - 指摘が **1 件以上** かつ **修正回数 < 2** → 3. へ進む
         - 指摘が **1 件以上** かつ **修正回数 ≥ 2** → 4. へ進む
       - ラウンド 2 以降は、`## 前回指摘の再検証` の `未解消` と `修正により新たな問題` の合計を **未解消** 件数、新規の指摘のうち `[2]` 以上の件数を **新規** 件数として、以下を上から順に判定する
         1. 未解消 **0 件** かつ 新規 **0 件** → ループを抜ける
         2. 新規 が前ラウンドの新規件数以上（ラウンド 1 の新規件数は、そのラウンドの `[2]` 以上の全件数）→ 指摘が収束せず揺れているとみなし、修正回数に関わらず 4. へ進む
         3. それ以外 → 修正回数 < 2 なら 3. へ、修正回数 ≥ 2 なら 4. へ進む
       - `解消` と `見送り容認` は未解消に数えない
    3. **修正**
       - 修正対象は、ラウンド 1 では `[2]` 以上の全指摘、ラウンド 2 以降では `未解消` と `修正により新たな問題` の指摘（位置は再検証節の記載に従う）に新規の `[2]` 以上の指摘を加えたもの
       - 指摘箇所を直接修正し、修正回数を 1 増やす
       - 指摘ごとに対処の記録を残す。次ラウンドの `## 前ラウンドの指摘と対処` ブロックの材料になる
         - R-ID（未採番なら出現順に `R000`, `R001`, ... を採番する）・重要度・位置・問題・提案（報告されたまま）
         - 対処（`修正` / `削除` / `見送り`）と対処内容（何をどう変えたか、または見送った理由）
         - 前回 `見送り容認` と判定された指摘は、対処 `見送り` のまま次ラウンドのブロックに引き継ぐ
       - **「次回起動するレビュアー集合」を、今回のラウンドで `[2]` 以上の指摘を出したレビュアー種別のみに更新する**
         （例: `@reviewer-for-comments` のみが指摘した場合、次回は `@reviewer-for-comments` のみで再レビュー）
       - 1. に戻る
    4. **上限到達時のユーザー判断**
       - AskUserQuestion で「レビューを完了とする / もう一度だけ修正を試みる / 中止する」を提示
         - 揺れ検知（2. の 2）で到達した場合は、収束していないためレビューを打ち切った旨と直近 2 ラウンドの新規件数を提示文に添える
         - 「レビューを完了とする」→ ループを抜ける
         - 「もう一度だけ修正を試みる」→ 3. に戻る（再度 4. に到達したら再びユーザー確認）
         - 「中止する」→ 実行を中止し、残った指摘内容をユーザーに報告

7. 最終レポートをユーザーに通知
  - 以下の形式で対応結果を列挙する
    ```
    ## 修正完了
    - 修正済み: f-a1b2c3d4, f-e5f6a7b8
    - 検証のみ: f-99887766（結果: ...）
    - blocked: f-11223344（理由: ...）
    - スキップ: f-55667788（理由: 未確定 / 対応しない / 採用案未指定 など）
    - 修正完了後レビュー: 指摘 N 件 / 修正 M 回
    ```

## 注意事項
- 人間のトリアージ判定は reviewview 側で管理する。本スキルはその判定を変更しない
- `triageReason` に技術的に従えない場合は、代替案で修正を進めず blocked で報告する
- 同じファイルへの修正が複数指摘で発生する可能性があるため、衝突が頻発する場合は ID を絞って複数回に分けて呼び出す
