---
name: fix:comments
description: 差分に含まれるコメントの品質を reviewer-for-comments でレビューし、その指摘に基づいてコメントを自動修正する。実装コードは変更せずコメントのみを直す。「コメントを直して」「コメントレビューして修正して」「fix:comments」などの依頼時に使用する。
argument-hint: [branch/tag/commit] [--target <絞り込み指定>]
---

このスキルは **レビュー（`@reviewer-for-comments`）と修正を一気通貫で行う**。人間のトリアージは挟まず、検出した指摘を全件修正する。

## 原則

- **修正してよいのはコメントのみ**。識別子・式・制御フロー・import・テストの assertion など実装コードは一切変更しない
- **コメントの新規追加は行わない**。`@reviewer-for-comments` は追加を指摘しないため、修正は既存コメントの書き換えと削除だけになる
- レビュー報告書ファイルは保存しない。指摘はセッション内で保持して修正に使う

## 引数

$ARGUMENTS を以下の2つに解析する:

- **diff 対象**（省略可）: 最初のフラグ以外の引数。branch/tag/commit を指定する。省略時はタスク 1. の「diff モードの決定」に従って自動決定する
- **`--target <絞り込み指定>`**（省略可）: レビュー対象ファイルを絞り込む自然言語の指定。`--target` の直後から次のフラグまたは末尾までを値として扱う（例: 「新規ファイルのみ」「認証に関係するファイルのみ」「`src/api/` 以下」）

## コンテキスト

- 渡された引数: $ARGUMENTS

## タスク

1. 引数を解析し、diff 対象・絞り込み指定を確定し、**diff モード** を決定する
   - diff 対象が指定されている場合 → **コミット比較モード**（指定された branch/tag/commit を diff 対象とする）
   - diff 対象が未指定の場合、以下を上から順に判定して最初に該当したモードを使う:
     1. `git diff --cached --name-status` の出力が空でない → **staged モード**（stage された内容のみをレビューする）
     2. `git diff --name-status` の出力が空でない → **worktree モード**（未コミットの変更を全てレビューする）
     3. どちらも空 → **merge-base モード**: デフォルトブランチ（`git symbolic-ref --short refs/remotes/origin/HEAD` で解決し、失敗時は `main`、それも実在しなければ `master`）と現在のブランチのマージベースを `git merge-base HEAD <デフォルトブランチ>` で求め、その SHA を diff 対象とする（以降はコミット比較モードとして扱う）
   - 未追跡（untracked）ファイルはどのモードでも判定・レビュー対象に含めない

2. レビュー対象ファイル一覧を取得する（A=新規 / M=既存変更 などのステータスは絞り込み判定に使う）
   - コミット比較モード: `git diff --name-status <diff対象>` を実行する
   - staged / worktree モード: Step 1 の判定で実行した `git diff --cached --name-status` / `git diff --name-status` の出力をそのまま使う
   - あわせて **BASE ハッシュ** をフル 40 桁 SHA-1 で解決し、最後まで保持する（再レビューの差分取得に使う）:
     - コミット比較モード / merge-base モード: `git rev-parse <diff対象>` の結果を `base_commit` とする
     - staged / worktree モード: `git rev-parse HEAD` の結果を `base_commit` とする
   - コミット比較モードでは `git rev-parse HEAD` の結果を `head_commit` として保持する（初回レビューの差分取得に使う）

3. 絞り込み指定がある場合、ステータス・ファイルパス・必要に応じて差分内容から該当性を判断し、ファイル一覧を絞り込む

4. コメントレビューが成立しないファイルを一覧から除外する
   - **削除ファイル**（ステータス D）— 直すコメントが残っていない
   - **スタンドアロンのドキュメント**（`.md` / `.mdx` / `.txt` など）— `@reviewer-for-comments` はソースファイルに埋め込まれたコメントだけを対象とし、ドキュメントファイルは範囲外
   - **コメント構文を持たないファイル**（`.json` / `.lock` / 画像・バイナリなど）
   - 残ったファイルが 0 件の場合は、除外した内訳とともにその旨をユーザーに通知して終了する

5. **1 ファイルにつき 1 つの `@reviewer-for-comments` 呼び出し**を TaskList に1タスクとして登録し、依存関係を持たせずに **並列実行** する
   - `Agent` ツールの `model` パラメータには **常に `opus`** を指定する。差分行数やファイル種別によって切り替えてはならない
   - サブエージェントへの入力は **対象ファイルの差分のみ**:
     - コミット比較モード / merge-base モード: `git diff <base_commit> <head_commit> -- <filepath>`
     - staged モード: `git diff --cached -- <filepath>`
     - worktree モード: `git diff -- <filepath>`
   - **ファイル全体は渡さない**。差分だけでは判断できない場合に限り、サブエージェント側の判断で当該ファイルを Read することを許容する
   - サブエージェントへの指示に「各指摘には差分のハンク行番号に基づく `**位置**` 欄（new 側の行番号を優先）を必ず記載すること。行番号はハンクヘッダー `@@ -a,b +c,d @@` を起点に、new 側なら `+` 行と文脈行のみを数えて算出すること」を含める

6. 全レビュー結果を統合し、指摘集合を組み立てる
   - 各指摘に出現順で `R000`, `R001`, ...（R + 3桁ゼロパディング連番）を採番し、重要度（`[2]` / `[1]`）・`**位置**`・`**問題**`・`**理由**`・`**提案**` を構造化して保持する
   - **`**位置**` のファイルパス単位でグループ化する**。コメント指摘は同一ファイルに集中するため、修正は指摘単位ではなくファイル単位で並列化する（指摘単位で並列起動すると同一ファイルへの書き込みが衝突する）
   - `**位置**` が `なし` の指摘は修正対象にできない。タスク 9 の最終レポートで本文をそのまま列挙する
   - 修正対象の指摘が 0 件の場合は、その旨をユーザーに報告して終了する

7. 修正対象ファイルごとにタスクを TaskList に登録する
   - subject: `[{ファイル名}] コメント指摘 N 件を修正` 形式
   - description: そのファイルに紐づく指摘全文
   - 依存関係（addBlockedBy）は設定しない（全件並列実行可能）

8. 修正 → 再レビューのループを実行する（修正は最大 2 回まで）
   - 修正回数カウンタを 0 で初期化する
   - 初回の修正対象は `[2]` / `[1]` を問わず全指摘とする

   1. **修正実施**
      - ファイル単位のタスクごとに TaskUpdate でステータスを `in_progress` に変更し、実装エージェントを **並列起動** する
      - エージェント種別はファイルパスで決める: `*.test.ts` / `*.spec.ts` / `__tests__/` 配下 → `@test-implementer`、それ以外 → `@code-implementer`
      - 完了後、各タスクの TaskUpdate でステータスを `completed` に変更する
      - 修正回数カウンタを 1 増やす
   2. **再レビュー**
      - 今回修正したファイルのみを対象に `@reviewer-for-comments` を **並列起動** する（モデルはここでも `opus` 固定）
      - 渡す差分は全モード共通で `git diff <base_commit> -- <filepath>`。作業ツリーを比較先にすることで、元の変更と今回の修正の両方が差分に含まれる
      - staged モードでは未ステージの変更も差分に含まれる。レビュー対象（ステージのみ）とずれる可能性がある旨をタスク 9 の報告に明記する
   3. **判定**
      - `[2]` 推奨の指摘が **0 件** → ループを抜ける
      - **1 件以上** かつ **修正回数 < 2** → 修正対象を `[2]` の指摘のみに絞り、指摘が出たファイルについて 7. と同じ形式でタスクを **新規登録し直して** 1. に戻る（前ラウンドのタスクは `completed` のまま残す）
      - **1 件以上** かつ **修正回数 ≥ 2** → 4. へ進む
   4. **上限到達時のユーザー判断**
      - AskUserQuestion で以下を提示する（選択肢はこの順で並べる）
        - 「このまま完了する」→ ループを抜ける
        - 「もう一度だけ修正する」→ 3. の 2 番目の分岐と同じ絞り込みを行って 1. に戻る（再度 4. に到達したら再びユーザー確認）
        - 「中止する」→ 実行を中止し、残った指摘内容をユーザーに報告する

   サブエージェントに渡すプロンプトは以下の構造で統一する（`@code-implementer` / `@test-implementer` どちらの場合も本文は共通）:

   ```
   {ファイルの絶対パス} のコメントに対するレビュー指摘を修正してください。

   ## 指摘一覧
   {このファイルに紐づく指摘を R-ID 付きで全件貼り付ける。重要度・位置・問題・理由・提案を含める}

   ## 制約
   - **修正してよいのはコメントのみ**。識別子・式・制御フロー・import・テストの assertion など実装コードは一切変更しない
   - コメントの新規追加はしない。既存コメントの書き換えと削除のみ行う
   - 修正対象は {ファイルの絶対パス} のみ。他のファイルには触れない
   - 各指摘の `**提案**` に従う。提案が削除であればコメントごと削除する
   - 指摘の内容が現在のコードと合わず修正できない場合は、無理に直さずその R-ID と理由を報告する

   ## 報告
   指摘 ID ごとに「何をどう直したか」、または「直せなかった理由」を1行で報告する
   ```

9. 最終レポートをユーザーに通知する

   ```
   ## コメント修正完了
   - diff モード: {モード名}（対象: {diff対象}）
   - レビュー対象: N ファイル（除外: M ファイル）
   - 検出した指摘: [2] N 件 / [1] M 件
   - 修正済み: R000, R001, R005
   - 未修正: なし
   - 再レビュー: 残指摘 N 件 / 修正 M 回
   ```

   - `未修正` には、実装エージェントが修正できなかった指摘、`**位置**` が `なし` で修正対象にできなかった指摘、上限到達後にユーザーが完了を選んだ際に残った指摘を、R-ID と理由つきで列挙する
   - staged モードで再レビューの差分に未ステージの変更が混ざった場合はその旨を明記する

## 注意事項

- タスクの進捗はいつでも TaskList で確認可能
- 実装エージェントの報告に **コメント以外の変更** が含まれていた場合は、その内容を最終レポートに明記する（原則違反として利用者が検知できるようにする）
- 同一ファイルの指摘は 1 つのエージェントにまとめて渡すため、指摘同士が矛盾する場合（片方が削除、片方が書き換えを提案）はエージェント側で解決される。解決内容は報告に含めさせる
