## コンテキスト
- 引数: $ARGUMENTS

## 引数解析

`$ARGUMENTS` をスペース区切りでトークン化し、次のように判定する。

- 数字のみのトークンは PR 番号として採用する（任意。省略時は現在のブランチから解決する）
- `PB-` に続けて数字が並ぶトークン（例: `PB-123`）はチケットIDとして採用する（任意・1件のみ。複数指定された場合は最初のものを使う）
  - 大文字小文字は問わず受け付けるが、タイトルに埋め込む際は `PB-123` のように `PB` を大文字へ正規化する
  - 数字のみのトークンはチケットIDとして扱わない（PR番号との衝突を避けるため、チケットIDは必ず `PB-` プレフィックス付きで指定する）
- その他のトークンは無視する

## タスク

ユーザーへの確認は「既存本文の上書き確認」（手順4）のみとし、それ以外のドメイン決定・タイトル選択・本文確認ではユーザーに質問しない。

### Phase 1: PR特定

1. PR番号が引数で渡された場合はそれを使用する
2. PR番号が渡されない場合は現在のブランチから解決する
   - `gh pr view --json number,title,state` を実行する（引数なしの `gh pr view` は現在のブランチに紐づく PR を返す）
   - コマンドが失敗した場合は、他のPRを探すフォールバックを行わず**即座に処理を終了する**
     - PR が存在しないブランチでは `no pull requests found for branch "<ブランチ名>"` を出力して終了コード 1 になる
     - 「現在のブランチに紐づく PR が見つかりません。PR 番号を引数で指定してください。」とユーザーに通知してから終了する
   - `state` が `OPEN` 以外（`CLOSED` / `MERGED`）だった場合は、「現在のブランチの PR #<番号> は <state> のため更新できません。」とユーザーに通知し、**即座に処理を終了する**
   - `state` が `OPEN` の場合はそのPRを採用し、以降の処理へ進む前に「PR #<番号> <タイトル> を対象にします」とユーザーへ通知する

### Phase 2: 情報収集

3. 対象PRの現在の内容・コミットを一括確認
   - `gh pr view <PR番号> --json title,body,commits --jq '{title,body,commits:[.commits[].messageHeadline]}'`
4. 既存本文の上書き確認
   - 取得した `body` から次の要素を取り除き、何も残らなければ「未記入」とみなす
     - HTML コメント、見出し行（`## ...`）、未チェックのチェックボックス行（`- [ ] ...`）、番号だけの行（`1.` など）、空白
     - PR 作成時に `reference/pr_template.md` の雛形がそのまま入っているだけの本文を、未記入として扱うための判定とする
   - 未記入の場合は確認せずに次の手順へ進む
   - 何か書かれている場合は、必ず AskUserQuestion で「既存の本文を書き換えるか」を尋ねる（この確認は省略してはならない）
     - 選択肢は「書き換える」「中止する」の2つとする
     - 「中止する」が選ばれた場合は「PR #<番号> の更新を中止しました。」と通知し、**即座に処理を終了する**
5. `reference/pr_template.md` を読み込み、PRのフォーマット（セクション構成）を把握
6. 過去PRから書き方・文体を把握
   - `bun run "${CLAUDE_SKILL_DIR}/scripts/fetch_past_prs.ts"`
   - 出力は JSON 配列（number, title, body）。キャッシュから取得するため通常は GraphQL 呼び出しが発生しない
   - キャッシュを強制更新したい場合: `bun run "${CLAUDE_SKILL_DIR}/scripts/fetch_past_prs.ts" --refresh`
   - スクリプトが失敗した場合（レートリミット超過等）はこのステップをスキップし、テンプレートと変更内容のみを元に本文を作成する
7. 対象PRの変更内容を確認
   - 変更規模の把握: `gh pr diff <PR番号> --stat`（まず全体の変更規模を把握する）
   - 変更ファイル一覧: `gh pr diff <PR番号> --name-only`
   - diffが大きい場合（目安: 500行以上）は、ファイル単位で `gh pr diff <PR番号> -- <ファイルパス>` で確認する
   - diffが小さい場合は全体を一括で確認してもよい

### Phase 3: タイトル・本文作成

8. タイトル候補を3つ作成
   - タイトル形式はチケットIDの有無で分岐する（上から順に判定し、最初に合致したものを採用する）
     - チケットIDが引数で指定された場合は `[PB-123] <type>(ドメイン): <説明>` とする（3候補すべての先頭に実際のチケットIDを必ず付ける。実番号のためユーザーによる置換は不要）
     - チケットIDが指定されていない場合は `<type>(ドメイン): <説明>` とする（従来どおり Conventional Commits 形式）
   - 3候補の差異は `<type>(ドメイン): <説明>` 部分のみで作り、`[PB-123]` プレフィックスは全候補で共通とする
   - **type** は diff の内容から判断する（`feat` / `fix` / `refactor` / `chore` など）
   - **ドメイン** は以下のルールで決定する
     - diff の変更内容がスケジュール機能に関するものであれば、ドメインを「スケジュール」とする
     - それ以外の場合は diff（変更ファイルパス・変更内容）からドメインを推測する。推測根拠（どのファイル群を見てどう判断したか）は Phase 4 の通知に含めるため記録しておく
   - **説明** は日本語で変更内容を簡潔に表現し、異なる観点（目的/手段/影響範囲など）から3候補を作成する
9. テンプレートのフォーマットに従い、過去PRの書き方を参考にして本文を作成
   - テンプレートのHTMLコメントも含めて省略せずに再現する
   - 各セクションは次のガイドラインで記述する
     - Summary には変更の目的と内容を日本語で簡潔に記述する。「なぜこの変更が必要か」と「何を変更したか」を含める
     - Classification は diff の内容から判断してチェックを入れる。新機能追加→Feature、不具合修正→Bugfix、リファクタリング・設定変更等→Others
     - How to confirm は、Classification が Feature または Bugfix の場合と Others の場合で書き分ける
       - Feature / Bugfix（UI操作を伴う変更）の場合は、番号付きリスト＋ネストした箇条書きで記述する
         - 番号付きの各ステップには下記の例のように「どの状態で何を操作するか」を書き、末尾を「以下を確認」で締める
         - 各ステップの下にネストした `-` で具体的な確認項目を列挙する
         - 確認項目には具体的な値・条件を含める（例:「10件以上」「3ヶ月ごと」「終日」など）
         - デグレッションチェックが必要な項目には「（デグレチェック）」と付記する
         - 例:
           ```
           1. 〇〇の状態で△△を行い以下を確認
              - 確認項目A（具体的な値を含める）
              - 確認項目B（デグレチェック）
           2. 別の操作を行い以下を確認
              - 確認項目C
           ```
       - Others（リファクタリング・コードのみの変更）の場合は散文形式で記述する
         - 次の例のように、レビュアーに確認すべきファイルや箇所を案内する
           ```
           コードの確認は〇〇を中心にざっくり確認して頂ければと思います。
           ```
     - Remarks にはレビュアーへの補足情報、注意点、影響範囲、今後の対応予定などを書く。特になければ「特になし」

### Phase 4: タイトル選択・更新

10. 後述「タイトル選択ルール」に従いタイトル3候補から最適な1つを選び、後述「選択結果の出力形式」でユーザーに通知する
11. 生成した本文をそのまま使用し、PRを更新（`gh pr edit <PR番号> --title "..." --body "..."`）
12. 更新結果をユーザーに報告（採用したタイトル・選択理由・ドメイン推測根拠を含める）

## タイトル選択ルール

3つのタイトル候補から最適な1つを選択する。基準は次の優先度順に適用する。

1. 変更の主題を最も正確に表現しているタイトルを優先する（正確性）
2. 抽象的すぎず詳細すぎないものを優先する（粒度の適切さ）
3. 同程度に正確であれば、より簡潔なタイトルを優先する（簡潔性）

### 選択結果の出力形式

PR 更新前に、次の形式でユーザーに表示する。ドメイン推測根拠の行は、スケジュール以外を推測した場合のみ表示する。

```
選択されたタイトル:
> {選択されたタイトル}

選択理由: {なぜこのタイトルが最適と判断したかの1文の説明}

ドメイン推測根拠: {どのファイル群を見てどう判断したか}
```
