## コンテキスト
- 指定の実装計画書: $ARGUMENTS

## 進捗管理の方針

- **進捗の正（source of truth）は実装計画書ファイルそのもの**。各ステップ見出しのチェックボックス（`- [ ]` / `- [x]`）が唯一の完了記録である
- 計画書へ書き込むのは**完了時の `- [x]` だけ**。「着手中」のような中間状態はファイルへ書かない。どのステップに着手済みか・どのサブエージェントへ委譲済みかは、このセッションのコンテキスト内で追跡する
  - 未完了を一律 `- [ ]` に保つことで、中断後は計画書を読み直すだけで残作業が確定する
- チェックボックスの書き換えは実装サブエージェント（`code-implementer` / `test-implementer`）が完了時に行う。本スキルは完了報告を受けた後に計画書を読み直し、`- [x]` になっていないステップがあれば自ら `- [x]` へ書き換える

## タスク

1. 実装計画書のファイルを特定する
  - 「指定の実装計画書」が指定された場合は、それを選択
  - 「指定の実装計画書」が指定されていない場合は、現在のセッションで作成された実装計画書を選択
  - 現在のセッションで作成された実装計画書がない場合は、 最新の実装計画書を5件取得し、AskUserQuestion でユーザーに選択させる

2. 選択した実装計画書の概要をまとめ、実行確認を行う
  - 既に `- [x]` のステップがある場合は、中断された実行の再開である旨と残りの未完了ステップ数を概要に含める
  - 「指定の実装計画書」に `-y` フラグが含まれている場合は、確認をスキップしてそのまま実行に進む
  - `-y` フラグがない場合は、AskUserQuestion でこの実装計画書で実装計画を実行してよいかユーザーに最終確認する
    - 選択肢は必ず「実行する」「実行しない」の順で並べる

3. 実装計画書のステップと依存関係を読み取る
  - 計画書を読み、全ステップについて以下をコンテキストに保持する
    - ステップ番号・タイトル・チェックボックスの状態（`- [ ]` / `- [x]`）
    - `**難易度**` と `**担当**`
    - `**ステップ依存関係**` の `blockedBy` / `blocks` / `並列グループ`
  - `**ステップ依存関係**` の記載がないステップは、直前のステップに依存する（直列）ものとして扱う
  - コードレビュー（手順 7）は計画書のステップではないためチェックボックスを持たない。全ステップ完了後に必ず実施する工程としてコンテキスト内で覚えておく
  - **実装に着手する前に現在のコミットハッシュ（`git rev-parse HEAD`）を「レビューのベースライン」として記録する**
    - 手順 7 のレビューで各レビュアーに渡す累積差分の起点になる

4. 計画書のチェックボックスで未完了ステップを確認
  - 全ステップが `- [x]` なら、既に実装済みである旨をユーザーに通知
  - `- [ ]` のステップがあれば5.に進む

5. 次の未完了ステップを実行
  - `- [ ]` のステップのうち、`blockedBy` に挙がったステップが**すべて `- [x]`** になっているものを実行可能とする
    - 同じ `並列グループ` に属する実行可能なステップは同時に実行してよい
    - `blocks` は依存関係の対称記載である。判定には `blockedBy` を使い、`blocks` は `blockedBy` の記載漏れを疑うときの突き合わせに使う
  - **各実行可能ステップについて、起動する実装エージェント種別を判定する**（起動するのは 1 ステップにつき 1 種類、集合ではない）
    - 計画書に `**担当**` が記載されている場合はそれに従う
    - **テスト実装ステップの場合**: `@test-implementer`
    - **それ以外の場合**: `@code-implementer`
    - **「テスト実装ステップ」の判定基準**: 当該ステップの変更対象ファイルが `*.test.ts` / `*.spec.ts` / `__tests__/` 配下のファイル**のみ**で構成されている場合
    - 判定が曖昧な場合は `@code-implementer` を選択する（本体コードを含むステップも扱える広い守備範囲で安全側）
  - 単一ステップの場合:
    - 着手するステップ番号をコンテキストに控える（計画書には書かない）
    - 判定結果に応じて `@test-implementer` または `@code-implementer` サブエージェントを利用して実装
    - 完了後、計画書を読み直し、当該ステップ見出しが `- [x]` になっていなければ `- [x]` へ書き換える
  - 複数ステップが並列実行可能な場合:
    a. 実装計画書の難易度情報を参照し、各ステップを「難易度: 高」と「それ以外」に分類
    b. 「難易度: 高」のステップが1つ以上ある場合 → チーム実行フロー（5-A）へ
    c. 「難易度: 高」のステップがない場合 → 通常並列フロー（5-B）へ

5-A. チーム実行フロー（難易度: 高の並列ステップ）
  1. TeamCreate でチームを作成（チーム名: `impl-{計画書名の略称}`）
  2. 難易度: 高の各ステップに担当チームメイトを割り当て、「ステップ番号 ↔ チームメイト名 ↔ サブエージェント種別」の対応表をコンテキスト内に保持する
     - この対応表は計画書に書かない。計画書へ書き込むのは完了時のチェックボックスのみ
  3. 各ステップに対応するチームメイトを Agent ツールで起動
     - 起動するサブエージェント種別は、ステップ 5 冒頭の判定基準に従い `@test-implementer` または `@code-implementer` を選ぶ（判定はステップ単位で個別に行うため、同一チーム内で両種が混在してよい）
     - team_name パラメータを設定
     - name: `step-{ステップ番号}` 形式
     - プロンプトに実装計画書のパスと担当ステップ番号を明記
  4. 難易度: 中/低のステップは通常通り Agent で並列起動（チーム外）。起動するサブエージェント種別はステップ 5 冒頭の判定基準に従う
  5. 全チームメイトの完了報告を待つ（メッセージは自動配信される）。誰がどのステップを担当しているかは 2. の対応表で照合する
  6. 全ステップ完了後:
     - 各チームメイトに SendMessage type: "shutdown_request" を送信
     - TeamDelete でチームを削除
     - 計画書を読み直し、このバッチで実行したステップ見出しが `- [x]` になっていなければ `- [x]` へ書き換える

5-B. 通常並列フロー（難易度: 高なしの並列ステップ）
  - 着手するステップ番号と割り当てたサブエージェント種別をコンテキストに控える（計画書には書かない）
  - 各ステップについてステップ 5 冒頭の判定基準に従い、`@test-implementer` または `@code-implementer` サブエージェントを並列に起動して実装（判定はステップ単位で個別に行うため、同一並列バッチ内で両種が混在してよい）
  - 完了後、計画書を読み直し、このバッチで実行したステップ見出しが `- [x]` になっていなければ `- [x]` へ書き換える

6. 計画書を読み直して `- [ ]` のステップが残っているか確認し、残っていれば5.を繰り返す

7. 全ステップ完了後、コードレビューを実行
  - コードレビューは計画書のステップではないため、チェックボックスの更新対象ではない
  - **次回起動するレビュアー集合**（次のラウンドで並列起動するサブエージェントの種類の集合。レビュー対象のファイルではなくサブエージェント種別のリスト）を初期化する
    - テストコードの場合: `@reviewer-for-test-code`, `@reviewer-for-comments`
    - それ以外: `@reviewer-for-logic`, `@reviewer-for-design`, `@reviewer-for-security-performance`, `@reviewer-for-comments`
  - 修正回数カウンタを 0 で初期化し、以下のレビュー→修正ループを実行する（修正は最大 2 回まで）
    1. **レビュー実施**
       - 「次回起動するレビュアー集合」に含まれるサブエージェントを**並列**で起動してレビュー
       - **各レビュアーには、ベースライン（手順 3 で記録したコミット）から現在までの累積差分を `git diff <ベースライン>` で取得し、その unified diff 本文をプロンプトに含めて渡す**
         - レビュアーはシェル・git を持たず自力で差分を取得できないため、ファイルパス・diff の範囲指定・コミット参照だけでは対象として不十分
         - **2 ラウンド目以降も、直前の修正分ではなく同じベースラインからの累積差分を渡す**
           - コメントの肥大化のように、変更後の全体像を見て初めて成立する検出基準があるため、範囲を直前の修正分に狭めると素通りする
    2. **判定**
       - `[2]` 推奨以上（`[2]`/`[3]`）の指摘が **0 件** → ループを抜ける
       - 指摘が **1 件以上** かつ **修正回数 < 2** → 3. へ進む
       - 指摘が **1 件以上** かつ **修正回数 ≥ 2** → 4. へ進む
    3. **修正**
       - 指摘箇所を直接修正し、修正回数を 1 増やす
       - **コメントに対する指摘は、説明を追記して辻褄を合わせる前に、当該記述ごと削除できないかを先に検討する**
         - ループの抜け条件が「指摘 0 件」であるため、再指摘を確実に避けられる追記が構造的に選ばれやすく、ラウンドを重ねるほどコメントが肥大化する
         - 記述を削除して指摘の前提ごと消すのも、指摘に答えた正当な対処
         - 説明を足す場合は同時に不要な記述を削り、コメント全体を修正前より長くしない
       - **「次回起動するレビュアー集合」を、今回のラウンドで `[2]` 以上の指摘を出したレビュアー種別のみに更新する**
         （例: `@reviewer-for-comments` のみが指摘した場合、次回は `@reviewer-for-comments` のみで再レビュー）
       - 1. に戻る
    4. **上限到達時のユーザー判断**
       - AskUserQuestion で「レビューを完了とする / もう一度だけ修正を試みる / 中止する」を提示
         - 「レビューを完了とする」→ ループを抜ける
         - 「もう一度だけ修正を試みる」→ 3. に戻る（再度 4. に到達したら再びユーザー確認）
         - 「中止する」→ 実行を中止し、残った指摘内容をユーザーに報告
  - ループを抜けたらレビュー工程を完了とし、8. に進む

8. 実装計画書のタイトルに「（実装完了）」と追記

9. 全ての作業が完了した旨をユーザーに通知

## 注意事項
- 進捗はいつでも実装計画書のチェックボックスで確認できる。実行を中断しても、計画書を開けば `- [ ]` のステップが残作業として残っている
- チーム実行中にチームメイトがエラーや問題を報告した場合は、SendMessage で指示を送り対処する
- チームメイトが応答しなくなった場合は、shutdown_request を送信してから手動で対処する
- チーム実行の途中で中止する場合は、全チームメイトをシャットダウンしてから TeamDelete を行う
