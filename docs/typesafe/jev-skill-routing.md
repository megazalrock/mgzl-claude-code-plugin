# Jev によるスキル / サブエージェント / MCP ツール選択

作成日: 2026-09-18
出典: TypeSafe AI 公式ドキュメント（Skill suggestion クックブック、Jev 1.13 jaggedness）

---

## 1. 何を解く話か

エージェントが多数のスキル（または サブエージェント / MCP ツール）を抱えると、
選択の判断材料が「1行に切り詰められた説明文」しかなくなる。結果として

- 似た名前の別スキルを読み込む（例: `.pptx` を**編集**するスキルと**生成**するスキル）
- どのスキルも不要なターンで、名前が並んでいるだけで何かを読み込む

という誤りが起きる。公式クックブックの計測では、182 スキルのロスターに対して
素のエージェントで **誤ロード 16.8% / 不要ロード 9.8%**。

これを Jev の 2 リクエストで前処理し、**誤ロード 7.3% / 不要ロード 4.0%**（約 2.3〜2.4 倍改善）
まで下げた、というのが元ネタ。正解を直接与えた上限値（オラクル）が 2.5% / 1.2% なので、
ギャップの大半を埋めている。

> 計測条件: 488 リクエスト（315 件はいずれかのスキルが該当、173 件は該当なし）、
> `jev-1.12` + `claude-haiku-4-5-20251001`。数値は自分のロスターで測り直すこと。

## 2. Jev 側の前提

| 項目 | 内容 |
| --- | --- |
| 入力 | `state`（文字列 / オブジェクト）+ 型付き `questions` |
| プリミティブ | `Noul`（真偽の確率）/ `Choice`（選択肢＋各候補の確率＋confidence）/ `Score`（順序尺度） |
| 並列性 | 同じ state に対する質問は 1 リクエストにまとめて並列評価される。質問を増やしても往復は増えない |
| Choice の上限 | 255 候補。超える場合はチャンクに分けてランキングし、勝者に対して同じ絞り込みを再実行 |
| コンテキスト | `state` + 全 `questions` で 64k トークン、`state` + 最長の質問 1 つで 32k トークン |
| 応答時間 | 公式デモの実測で 0.09〜0.31 秒程度 |

API エンドポイントやパラメータ名は公式 API リファレンス（docs.typesafe.ai）で確認すること。
公式クックブックのコードは Python SDK（`typesafe-sdk`）。TypeScript から使う場合の
公式 SDK の有無は未確認なので、HTTP を直接叩くかどうかも含めてドキュメントを参照。

## 3. 構成（2 コール）

```
ユーザーのターン
   ↓
[Call 1] 全ロスターを浅く読む
   - Choice "which": 全スキル。criteria = 各スキルの 1 行説明（インデックスと同じ文面）
   - Noul x3 "gate::*": そもそもスキルが要るターンか
   ↓ gate が閾値未満 → 何も提案しない
   ↓ 上位 3 件
[Call 2] 3 件だけ深く読む
   - Choice "which": 候補 3 件。criteria = 完全な説明 + SKILL.md 冒頭 700 文字
   - Noul "fits::{name}": 候補ごとに「この依頼が求めていることを実際にやるスキルか」
   ↓ fits の最大値が閾値未満 → 何も提案しない
   ↓
勝者 1 件をシステムプロンプトに 1 行だけ足す
```

### gate 用の 3 つの Noul（そのまま流用可）

主題（ソフトウェアかどうか等）を聞くと「モナドとは何か」のような質問が弾けない。
**行動を求めているか**を聞くのがポイント。

1. `acts_on_user_system` — ユーザーのファイル・アカウント・デバイス・サービスに対して
   「操作」を求められているか（説明や助言だけではないか）
2. `would_follow_documented_procedure` — 熟練者ならこれに答えるとき、特定の手順書や
   コマンド集を参照するか（一般知識で答えるのではなく）
3. `prose_suffices` — 知識のある人がツールも資料もアクセス権もなしに、文章だけで
   完全に満たせる依頼か（**これだけ反転**して集計）

3 つの平均が閾値未満なら提案しない。

### 閾値（クックブックの初期値。自分のデータで調整する）

| 定数 | 値 | 意味 |
| --- | --- | --- |
| `SHORTLIST` | 3 | Call 1 から Call 2 に渡す候補数 |
| `EXCERPT_CHARS` | 700 | Call 2 の criteria に入れる SKILL.md 冒頭の文字数 |
| `GATE_THRESHOLD` | 0.30 | gate 3 問の平均。これ未満なら提案なし |
| `FITS_THRESHOLD` | 0.30 | `fits` の最大値。これ未満ならショートリストごと破棄 |

## 4. ロスターの形

各エントリに 4 つのフィールドがあれば足りる。スキルでもサブエージェントでも MCP ツールでも同じ。

```json
{
  "name": "pptx-author",
  "category": "documents",
  "description": "Build PowerPoint decks headless with python-pptx.",
  "description_full": "（切り詰めていない完全な説明文）",
  "body": "（SKILL.md 冒頭 1600 文字程度。Call 2 で先頭 700 文字を使う）"
}
```

- Call 1 の criteria = `description`（エージェント自身が見ているのと同じ 1 行）
- Call 2 の criteria = `description_full` + " — " + `body` の先頭 N 文字

MCP ツールに当てはめる場合は、`description` = ツール定義の説明、`body` = 引数スキーマの要約や
使用例。**認可・実行可否・停止条件はモデルの答えの外**に置き、コード側のルールで持つこと。

## 5. エージェントへの渡し方

ロスター本文は**一切変えない**。提案はロスターの後ろに独立したブロックとして足す
（プレフィックスキャッシュを壊さないため）。

```
<skill_relevance>
Relevant to the current request: pptx-author. Ignore this if it does not fit what the
user actually asked for.
</skill_relevance>
```

文面の設計意図:

- **「合わなければ無視してよい」と明記する。** 強く押すと、誤った提案にも従ってしまう。
  誤った提案は提案なしより悪い。
- **提案が無いターンでも「該当なし」と 1 文送る。** 何も送らないと、ロスター側の
  「迷ったら読み込め」という指示が野放しになる。

## 6. 自分の環境への適用メモ

### 対象候補

- Claude Code の SKILL.md 群 → どれを読むべきか（本家のユースケースそのもの）
- サブエージェント定義 → どのサブエージェントに委譲するか
- MCP ツール → どのサーバー / ツールが該当するか

### 呼び出し箇所

`UserPromptSubmit` 系のフックで Call 1 → Call 2 を実行し、結果を 1 行注入する。
2 コールでも実測 0.1〜0.3 秒 × 2 なので体感を壊さない想定。

### フェイルオープン必須

タイムアウト（2〜3 秒）・API エラー・キー未設定のいずれでも、**提案なしで通常どおり続行**する。
ここで止まるとエージェント全体が止まる。

### 候補数が多い場合

Choice は 255 候補まで。それ以上は
「チャンクに分けてそれぞれランキング → 各チャンクの勝者に対してもう一度同じ絞り込み」。
182 件は 1 つの Choice に収まる規模。

## 7. 評価手順（実装より先に決めておく）

前回のトリアージの失敗（信頼度の帯で一致率に差が出ず、閾値で切り分けられなかった）を
繰り返さないため、**先に評価セットを作る**。

1. **ゴールデンセットを作る**
   - 該当スキルがあるリクエスト: 各 SKILL.md から生成した依頼文 + 正解スキル名
   - 該当なしのリクエスト: 日常的な依頼 / 技術的だがスキル不要な質問 /
     ロスターに無い対象を名指しする依頼（例: X 用スキルしかないのに Mastodon への投稿）
   - 後者は「当てずっぽう」を罰するために重要
2. **2 つの誤り率を測る**（どちらも低いほど良い）
   - 誤ロード率: 該当ありのうち、最初の読み込みが正解でなかった割合（何も読まないのも失敗）
   - 不要ロード率: 該当なしのうち、何かを読み込んでしまった割合
3. **3 本比較する**: 提案なし / Jev の提案あり / 正解を直接与える（＝上限）
4. **修正と破壊の両方を数える**
   クックブックでは 315 件中 37 件が改善し、7 件は提案のせいで壊れた。
   ネットで得か、必ず両方向を見る。
5. **確率の帯ごとの正解率を見る**（較正の確認）
   帯によって正解率が変わらないなら、そのタスクでは閾値運用は成立しない。
   その場合は「提案として出す」までに留め、自動制御には使わない。

## 8. Jev の既知の弱点（設計時の注意）

公式の jaggedness ページより。

- **文字どおりに読む** — 書いた指示どおりに答える。意図は汲まない。
  境界ケースは criteria に明記する。
- **多段の間接性に弱い** — 「プロパティのプロパティ」を辿るような質問は精度が落ちる。
  関係する state を名前で直接指す。
- **state が膨らむと精度が落ちる（context rot）** — 質問に必要なフィールドだけ送る。
  絞り込めない場合は Noul で関連性フィルタを先にかける。
- **数え上げ・日付比較・算術は不可** — コード側の仕事。
  数える場合は候補ごとに 1 問ずつ聞いて、合計はコードで取る。
- **敵対的な入力に引きずられうる** — state はデータであって敵対的とは見なされない。
  注入された指示や、自分の分類を主張するテキストは答えを動かしうる。
- **1 つの質問に複数の判断を詰めない** — 分解して、組み合わせはコードで行う。
