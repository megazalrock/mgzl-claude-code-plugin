# implementation-plan-creator への writing-plans 由来フォーマットの導入 タスク一覧

> **For agentic workers:** 本書はタスク一覧であり、確定タスク（Task 1〜7）と要相談項目（D1〜D3）に
> 分かれる。D1〜D3 はユーザーとの合意が取れるまで着手しないこと。
> ステップ追跡は checkbox（`- [ ]`）構文を使う。

**Goal:** `cbo/agents/implementation-plan-creator.md` に不足している「計画書という成果物の型
（フォーマット契約）」を、superpowers `writing-plans` スキルから移植する。計画の中身に関する
教訓群（既存の「計画書作成の指針」「実装設計の指針」）はそのまま維持する。

**Architecture:** 変更対象は 2 ファイル。判断・原則はエージェント本文
（`cbo/agents/implementation-plan-creator.md`）へ、出力の型は保存テンプレート
（`cbo/skills/document-saver/references/format-implementation-plan.md`）へ置く。
両者を触るタスクは、テンプレート側の競合を避けるため直列に実施する。

**Tech Stack:** Markdown のみ。スクリプト・コードの追加はしない。検証は `Grep` ツールによる
文字列検索と目視確認。

**参照元:** superpowers 6.2.0 `skills/writing-plans/SKILL.md`
（`https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md` と内容一致を確認済み）

### D1: 「タスク」と「ステップ」をどう分けるか（元 #6）— **決定: B 案**

**現状の事実（確認済み）:**

- 1 ステップ = `code-implementer` または `test-implementer` への 1 委譲
  （`cbo/agents/code-implementer.md:5` / `:46`）
- 両エージェントは**担当ファイル種別で分かれている**。`code-implementer` は本体コード専用で、
  新規テスト追加は責務外（`cbo/agents/code-implementer.md:79`）。テストは `test-implementer`

**そこから導かれる論点:**

superpowers の TDD サイクル（失敗テスト作成 → 実装 → 緑化を 1 タスク内で回す）は、
**1 ステップに収まらない**。テスト作成と本体実装が別エージェントである以上、最低 2 ステップに
分かれる。したがって「レビュー単位／テストサイクル単位」と「サブエージェント委譲単位」は
別の概念であり、これを 1 語（ステップ）で表現している現状に無理がある。

**選択肢:**

- **A 案: 二層導入（タスク > ステップ）**
  - タスク = 独立してテスト可能な成果物を産む単位。難易度・工数・Files・Interfaces はここに付ける
  - ステップ = 1 サブエージェント委譲。担当エージェントが確定する粒度
  - 影響: テンプレートの階層変更に加え、`impl:execute` 側の走査単位、`code-implementer` の
    計画書更新処理（`:82` の完了マーク付与）も追従が必要。**影響大**
- **B 案: 一層維持 + 「担当エージェント」フィールド追加（推奨）**
  - ステップの定義を「1 サブエージェント委譲」に明文化する
  - テンプレートのステップ雛形に `**担当**: code-implementer / test-implementer` を追加
  - TDD は「ステップ N: 失敗テスト作成（test-implementer）」→
    「ステップ N+1: 最小実装（code-implementer）」の連番で表現し、`blockedBy` で結ぶ
  - 影響: テンプレートのフィールド 1 個追加のみ。**影響小**
- **C 案: 一層のまま「TDD ペア」注記だけ導入**
  - 担当エージェントは書かず、ペア関係のみ注記する。B 案の劣化版

**決定は B 案。** 理由は 2 つ。

1. 既存の `impl:execute` / `code-implementer` はステップ番号ベースで動いており、二層化は
   実行側の改修を誘発する。得られる利益（レビュー単位の明示）に対して工数が見合わない
2. 依存関係の表現は既存の `blockedBy` / `blocks` / 並列グループで足りており、
   「タスク」層を新設しなくても TDD ペアは表現できる

**実行側の確認結果（`cbo/skills/impl__execute/SKILL.md`）:**

- ステップは `TaskCreate` で 1 タスクとして登録され、依存関係は計画書の記載に従う（`:23-30`）。
  ステップ番号ベースの運用で確定しており、B 案と整合する
- 起動するサブエージェント種別は「変更対象ファイルがテストファイルのみか」で実行時に**推測**して
  おり、曖昧な場合は `code-implementer` へ倒している（`:40-44`）。
  したがって `担当` フィールドの追加は新概念の導入ではなく、既存の暗黙判定の明示化にあたる
- **`impl__execute` 側の改修は本タスク群では行わない。** 計画書に `担当` があってもなくても
  現行の推測ロジックで動作するため、破壊的変更にならない

→ Task 8 として実装する。

### D2: チェックボックス構文で何が改善されるか（元 #7）— **決定: A 案（導入する）**

**現状の事実（確認済み）:**

- `cbo/agents/code-implementer.md:82` は「該当ステップに完了マーク（例: `- [x]`）」を
  付ける運用になっている
- しかし `cbo/skills/document-saver/references/format-implementation-plan.md` に

2. **残タスクの機械判定** — `- [ ]` の Grep count で未着手ステップ数が即座に出る。

### D3: TDD 採用時の書式をどこにどう定義するか（元 #8）— **決定: 案 A**

**論点 1: 定義場所（エージェント本文 or テンプレート）**

- テンプレート側は「保存時の型」、エージェント本文は「書くときの判断」。
  TDD 書式は**型**であるため、テンプレート側が本命
- ただし現行テンプレートは実装計画書 1 種類しかないため、TDD 版と非 TDD 版の切替を
  テンプレート内の条件付き節として表現する必要がある
- **推奨:** テンプレートに `### TDD 採用ステップの書式` 節を設け、エージェント本文からは
  「TDD を採用した場合はテンプレートの当該書式に従う」と 1 行参照する

**論点 2: 書式の中身**

superpowers 原型は 5 ステップ（失敗テスト作成 → 失敗確認 → 最小実装 → 成功確認 → コミット）。
本プロジェクトへの翻訳では以下の改変が必要。

- コミットステップは削除（`cbo/agents/implementation-plan-creator.md:353` の Git 操作記載禁止）
- RED と GREEN は担当サブエージェントが異なるため、ステップ境界をエージェント境界に合わせる

**提案書式（D1 の B 案を前提とした場合）:**

- ステップ N: 失敗するテストの作成と RED 確認（担当: test-implementer）
  — テストコード本体 + 実行コマンド + **期待される失敗内容**
- ステップ N+1: 最小実装と GREEN 確認（担当: code-implementer）
  — 実装コード + 実行コマンド + 期待される PASS

**論点 3: 「期待される失敗」をどこまで厳密に書くか**

superpowers は `Expected: FAIL with "function not defined"` のようにメッセージまで書かせる。
ただし型エラー文言は `vue-tsc` のバージョン差で揺れるため、完全一致を要求すると計画書が
すぐ陳腐化する。**部分一致レベル**（「`is not defined` を含む」等）に留める案を推す。

**論点 4: RED 確認を誰が実行するか（未決・最重要）**

これは報告形式の選択ではなく、**`test-implementer` の契約を変えるかどうか**の判断である。
現行の `test-implementer` は TDD の RED と真っ向から矛盾する前提を 2 つ持っている。

- `cbo/agents/test-implementer.md:50` — 「本体コード（SUT）は**既に存在することを前提**とし、
  その挙動を pin する形でテストを追加・修正します」
- `cbo/agents/test-implementer.md:82` — 「**全てのテストが成功するまで**修正する」

TDD の RED は「SUT がまだ無い／不完全な状態でテストを書き、失敗することを確認する」工程なので、
どちらの前提にも反する。**何もしなければ、RED ステップを渡された `test-implementer` は
緑にしようとして SUT を勝手に実装するか、テストを歪めて通す。** よって選択肢に関わらず
最低限の改修は必須である。

**選択肢:**

- **案 A: `test-implementer` が実行し、失敗の種類まで判定して報告する**
  - 判定を 3 分岐にする
    - 期待どおりの失敗（アサーション失敗 / 未実装シンボル参照）→ ステップ完了
    - 想定外の失敗（テスト自体の構文・import・セットアップ不備）→ 修正して再実行
    - **成功してしまった → 異常。停止して報告**（テストが何も検証していない
      = vacuous、または SUT が既に実装済み）
  - この 3 分岐は `cbo/agents/test-implementer.md:83` の既存の偽陽性チェック
    （SUT を仮 mutation して fail することを確認する）と思想が同一で、既存資産と整合する
  - superpowers が "Run it to make sure it fails" を独立ステップにしている理由もここにある。
    RED を確認しないと「常に通るテスト」を GREEN 前に検出できない
  - 改修範囲: `:50` の SUT 実在前提に例外を追加 / `:82` の全 green 要件を RED ステップで
    除外 / 報告形式に RED 確認結果欄を追加
- **案 B: 計画書に期待値を書くだけで、`test-implementer` は実行しない**
  - RED ステップではテストを書いて lint・型チェックのみ通し、テスト実行はしない
  - 緑の確認は GREEN ステップ（`code-implementer`）が実装後に行う
  - 改修範囲: `:82` に「RED ステップでは green を完了条件にしない」の一文のみ。最小
  - 代償: テストが本当に失敗するか誰も検証しない。そもそも動かないテスト（import 崩れ等）が
    GREEN ステップへ流れ、`code-implementer` が「自分の実装が悪いのかテストが悪いのか」の
    切り分けに苦しむ。vacuous なテストも検出されない
- **案 C: 実行はするが判定はしない（案 A の軽量版）**
  - `test-implementer` はテストを実行し、失敗メッセージを報告へ**転記するだけ**。
    期待どおりの失敗かの判定は親セッション／人間が報告を読んで行う
  - 改修範囲: 案 A とほぼ同じだが判定ロジックが不要
  - 代償: 異常（テストが通ってしまった等）で自動的に止まらない

**決定は案 A。** 理由は 3 つ。

1. 改修範囲は案 C とほぼ同じで、判定の 3 分岐を書き足すだけ。追加コストが小さい
2. 3 分岐の 3 つ目（成功してしまった）が、TDD で最も価値のある検出。
   これを捨てると RED ステップを設ける意味の大半が失われる
3. 既存の `:83`（仮 mutation による偽陽性確認）と同じ思想であり、
   `test-implementer` に新しい概念を持ち込まない

**案 A を採る場合、論点 3（期待失敗メッセージの厳密さ）の重要度が上がる。**
判定に使う値になるため、「部分一致レベル」の粒度をテンプレートで明確に規定する必要がある。

**実行側への影響:** `cbo/skills/impl__execute/SKILL.md` はステップ完了をサブエージェントの
完了報告で判断しているため、案 A・案 C いずれでも `impl__execute` の改修は不要と見込まれる
（`test-implementer` が「完了」と報告すれば通る）。ただし案 A の 3 分岐目（異常停止）が
発生したときの扱いは要検討。

**実装時に判断する残件（タスク内に工程として組み込み済み）:**

- 既存の `cbo/agents/implementation-plan-creator.md:134`（不可逆操作を含む計画での
  ベースライン確認ステップ 0）と、TDD の RED 確認の関係整理 → Task 10 Step 4
- 3 分岐目（異常停止）が `impl__execute` へ伝わるかの確認 → Task 11 Step 5

→ Task 10（計画書側の書式）と Task 11（`test-implementer` の RED モード対応）として実装する。
