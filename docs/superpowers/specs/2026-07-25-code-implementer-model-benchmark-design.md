# code-implementer モデル比較ベンチマーク設計（Sonnet vs Opus 5）

作成日: 2026-07-25

## 目的

`cbo/agents/code-implementer.md`（現在 `model: sonnet`）の model を Opus 5 へ切り替えるべきかを、TypeScript・Vue コンポーネント実装タスクにおける品質差とコスト差で判断するための材料を得る。

## 背景

- `code-implementer` は本体コード（非テスト）実装専門のエージェント。品質ゲート（eslint MCP・vue-tsc-runner・test-runner）と、蓄積された教訓（コーディング指針約 120 行）を持つ
- 呼び出し元は `impl:execute`（計画書ステップ）・`review:fix`（レビュー指摘修正）・単発タスクの 3 パターン
- ベンチマーク対象の業務リポジトリ: `/Users/otto/workspace/craftbank/arrangement-env/front`（Vue 3 + TypeScript。ビルド・テスト等は Docker 環境で実行される）

## 全体像

業務リポジトリのマージ済み過去タスク 3 件を「実装前コミット」の状態からリプレイする。同一の指示文で Sonnet / Opus 5 の `code-implementer` に各 1 回ずつ実装させ（計 6 実行）、客観ゲート + LLM ブラインド審査 + 人間確認で品質差を、トークン消費・所要時間でコスト差を測る。

比較条件の統制: 同一開始コミット・同一指示文・同一ツール環境・各モデル 1 回。

## 実行方式: 順次実行

worktree 並列方式は Docker 環境との互換が不確実なため採用せず、メインのチェックアウト上での**順次実行方式**で確定する。

タスクごとの手順:

1. 開始前に未コミット変更が無いことを確認する
2. 実装前コミット（正解 PR の親コミット）へ checkout する
3. 一方のモデルで `code-implementer` を実行する
4. 客観ゲート（Phase 4 参照）を再実行し、成果を patch（`git diff` 出力）として保存する
5. `git reset --hard` + `git clean` で開始状態へ巻き戻す
6. 他方のモデルで同様に実行・記録する
7. 全実行終了後、元のブランチへ復帰する

並列性は無いが Docker マウント問題を回避でき、3 タスク規模なら所要時間は許容範囲。比較条件（同一開始コミット・同一指示文・各 1 回）はこの方式で担保する。

## Phase 1: タスク選定

業務リポジトリのマージ済み履歴から、以下の条件で候補を発掘し、難易度別に数件ずつ提示する。ユーザーが最終的に 3 件を確定する。

選定条件:

- 作成者が Otto Kamiya のコミット / PR に限る
- マージが直近 2 ヶ月以内のものに限る
- 本体コード（非テスト）中心の変更で、Vue コンポーネントまたは TS ロジックを含む
- 変更規模で難易度を層別する（目安: 小 = 〜50 行 / 中 = 50〜200 行 / 大 = 200 行〜）
- 単一 PR（または単一コミット列）で完結しており、リプレイの開始コミット（実装前の親コミット）が明確
- 3 件でタスク種別が偏らないようにする（例: 新規コンポーネント作成・既存改修・ロジック実装から各 1 件）

候補ごとの提示内容: PR/コミットの概要、変更ファイル一覧、変更規模、リプレイに向く理由。

## Phase 2: タスク指示文の作成（リーク対策込み）

各タスクについて、PR 説明・コミットメッセージから「実装前に開発者へ渡されたであろう指示文」を復元起案する。

- 粒度は実運用の実装計画書ステップに合わせる。正解実装の内部詳細（関数名・具体的な実装方針・ファイル分割の答え）は指示文に書き込まない
- 正解を知っているユーザーがレビューし、情報リーク（正解を誘導する記述）を除去してから確定する
- 実行時のリーク対策: エージェントへのプロンプトに「git 履歴・リモートブランチ・reflog の参照禁止」を明示する
- 審査時のリーク検知: 正解実装と不自然に一致する箇所（コメント文面の一致等）がないかを審査観点に含める

## Phase 3: 実行（3 タスク × 2 モデル = 6 実行）

- Agent ツールで `code-implementer`（cbo プラグインのエージェント）を agentType 指定で呼び出し、呼び出し時の `model` パラメータで `sonnet` / `opus` をオーバーライドする（呼び出し時指定がエージェント定義の `model: sonnet` より優先される）
- 両モデルに同一の指示文を単発実装タスク形式で渡す
- 記録テンプレートへ以下を記録する:
  - 完了 / 未完了
  - 所要時間
  - トークン消費（Agent 実行結果から取得可能な範囲。取得できない場合は所要時間で代替し、その旨を記録する）
  - エージェント自己申告の品質ゲート結果（lint / 型 / テスト）
  - 報告内容の質（報告形式の遵守、test-implementer への引き継ぎ明記の有無など）
- 成果物は patch ファイル（`git diff` 出力）として結果保存ディレクトリへ保存する
- エラー対応: エージェントが途中で異常終了した場合は同条件で 1 回だけ再実行し、再実行した事実を記録する。2 回目も失敗した場合はそのタスク × モデルを「未完了」として記録する

## Phase 4: 評価（三段構え）

1. **客観ゲート**: 各成果物に対し eslint / vue-tsc / 関連テスト（変更ファイルに対応する既存テスト。test-runner スキルでの回帰チェックと同じ範囲）をベンチ実施者側で再実行し、pass / fail とエラー数を記録する（エージェントの自己申告と分離して検証する）。客観ゲートの再実行は巻き戻し前（各実行の直後）に済ませる（巻き戻し後の patch 再適用を不要にするため）
2. **LLM ブラインド審査**: 審査員は **fable のサブエージェント**（ユーザー明示指定。「サブエージェントに fable を使わない」通常ルールの例外として承認済み）。成果物を「実装 A / 実装 B」に匿名化し、どちらのモデルの成果物かを伏せて審査する。A / B へのモデル割当はタスクごとに入れ替え、審査員がラベルからモデルを推定できないようにする。採点軸は以下の 3 つ。各軸 5 段階評価 + 根拠となる指摘の列挙:
   - 正解実装（マージ済み diff）との機能的等価性
   - コーディング指針（code-implementer の教訓リスト）の遵守度
   - 設計品質（責務分離・命名・コメント品質）
   - 併せて正解丸写しの兆候の有無も確認する
   - 大規模タスクで diff が審査員のコンテキストに収まらない場合はファイル単位に分割して審査する
3. **人間の最終確認**: ユーザーが最低 1 タスク分の両モデルの diff を目視し、LLM 審査結果の妥当性を検証する

## Phase 5: レポート

以下を含む Markdown レポートを作成する:

- タスク × モデルの結果マトリクス（客観ゲート・審査スコア・トークン・時間）
- 総評（どの種別・難易度で差が出たか）
- 推奨アクション: 「opus へ切替」「sonnet 維持」「タスク種別・難易度で使い分け（呼び出し側の model オーバーライド運用）」のいずれか

### 切替判断の目安

- Opus が品質軸で明確に優位（3 タスク中 2 タスク以上で審査スコア優位、かつ客観ゲートが同等以上）で、コスト増（トークン・時間）が許容範囲 → opus へ切替
- 品質がほぼ同等 → sonnet 維持
- 大規模・複雑タスクのみ優位 → 使い分けを検討

## 成果物と保存場所

  - `runbook.md` — 実行手順書（Phase 0〜5 の具体的手順）
  - `record-sheet-template.md` — 記録テンプレート
  - `judge-prompt-template.md` — 審査プロンプトテンプレート
- **`$MGZL_DIR/benchmarks/2026-07-code-implementer-model-benchmark/`**: 実行データ（patch・記録実データ・審査結果・最終レポート）を置く。業務コード由来の断片を含むため、プラグインリポジトリには置かない

## リスクと対策

- **IDEA MCP ツールが利用できない状態（IDE 未起動等）で実行してしまう可能性** → 両モデルとも同条件であれば比較は成立するため、条件統制を優先する。実行前に IDEA MCP の可用性を確認し、6 実行すべてで同じ状態（全部使える / 全部使えない）に統一して記録する
- **正解リーク** → 指示文の人間レビュー + git 参照禁止の明示 + 審査時の丸写し検知
- **トークン計測の精度** → 取得可能な範囲で記録し、取得不能なら所要時間で代替する（記録に明記）
- **各 1 回実行のためモデル内ばらつきとモデル間差を区別できない** → パイロットの限界としてレポートに明記する。審査スコアが僅差の場合のみ該当タスクを追加実行して判定する
- **審査員のコンテキスト上限** → 大タスクはファイル単位に分割して審査する

## スコープ外

- worktree 並列実行方式（Docker 環境との互換が不確実なため、事前検証ごと見送り）
- `test-implementer` のモデル比較
- 統計的検定を目的とした 3 回以上の反復実行
- ハーネスの完全自動化（claude CLI headless 方式）
- `code-implementer.md` 本体の model 変更（ベンチ結果を見てユーザーが別途判断する）
