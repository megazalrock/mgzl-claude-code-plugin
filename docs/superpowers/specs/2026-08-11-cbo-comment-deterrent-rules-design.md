- 出典メモ: `/Users/otto/workspace/craftbank/arrangement-env/front/.mgzl/memo/20260811-042922-comment-verbosity-recurrence-lessons.md`（**読み取り専用**）
- 改訂の基準はあくまで**現行の `cbo/agents/*.md` の記述**。過去の計画書は参照しない

## 背景

`code-implementer` / `test-implementer` が「これを消すと壊れる」「ここを変えると〜になる」という意味のコメントを頻繁に生成している。ユーザーの指摘は「**コメントがないと消してしまう可能性がある**という意味コメントは完全に不要」。書いてあるものを消せば動かなくなるのは全てのコードに当てはまる自明の事実であり、コメントの存在理由にならない。

問題は「新しい禁止類型が抜けている」ことではない。**cbo プラグインが現に「壊れ方を書け」と指示している**ことにある。

- `code-implementer.md:176` / `test-implementer.md:132` — 「残す価値があるのは次の 4 つ: 1. これを外す・変えると何が壊れるか …」
- `code-implementer.md:178` / `test-implementer.md:135` — 「根拠は『この場所で何が壊れるか』で書く」
- `code-implementer.md:182` / `test-implementer.md:139` — 「『結論 + 壊れ方』の 1 セットへ圧縮する」
- `implementation-plan-creator.md:334` — 「コードコメントとして残すなら『順序を変えると何が壊れるか』の形へ書き換える」
- `reviewer-for-comments.md:167` — criterion 7 の保護筆頭が `What breaks if this is removed or changed`
- `reviewer-for-comments.md:119` / `:123` — 削除指摘の代替案として `what breaks here if this changes` / `conclusion + how it breaks` を提示

出典メモは、同一ファイルが 2 日で 2 回「冗長なコメントを整理」された事実を扱う。1 回目の整理（既存規約の抽出元）で**新設された** 6 行の JSDoc 集約ブロックが、2 回目でまるごと削除された。つまり**現行規約は否定された成果物を推奨例として抱えている**。

## 目的

1. 「将来の編集者への牽制」を目的としたコメントを生成側で書かせない
2. 検知側（`reviewer-for-comments`）が同じ類型を削除指摘として拾えるようにする
3. 同時に、**過剰削除へ振れないよう**残すべき類型を再定義する

## 非目的

- コメントの一律削減。出典メモは「一律削除ではない」と明記しており、外部挙動・仕様上の制約は維持された
- 既存の削除類型 A-1〜A-6（前例参照 / 相互参照 / ライブラリ内部解説 / 言い換え / 他コンポーネント仕様 / 推論連鎖）の変更。これらは今回も有効
- `knowledge-distiller.md` の変更。コメントから外した情報の退避先という記述は今回も有効
- コメント整理専用スキルの新設。整理タスク固有のルールは既存エージェントへ追記する

## 設計

### 1. 骨格 — 担保ゲート

「壊れ方を書け」という**書き方の指示**を、「そもそも書くか」を問う**関門**へ置き換える。生成側にコメント記述前の判定順序を置く。

1. その情報は **型・制御フロー・エラーメッセージ・テスト**のいずれかで既に担保されていないか → 担保されていれば書かない
2. 担保されていないとして、それは**コードを読む助け**か、**将来の編集者への禁止・牽制**か → 後者なら書かない。守りたい挙動はテストで守る
3. 残るのは「コードからは読み取れない事実」だけ。これを 1〜3 行で書く

このゲートは削除方向（何を書かないか）と保護方向（何を残すか）を単一の基準へ統合する。「壊れ方」は判定軸から外れ、ゲートを通ったかどうかだけが基準になる。

### 2. 保護類型の再定義

現行 4 類型の筆頭「①これを外す・変えると何が壊れるか」を削除し、出典メモの「今回残したもの」から再構成する。

**A. コードの外にしか存在しない事実**

- 外部の挙動（ライブラリ・フレームワーク・ブラウザ）でコードを読んでも分からないもの — 例: `undefined を渡すとクエリから削除される`
- 実際に踏んだ不具合と、その回避策を選んだ理由
- 仕様上の制約・既知の乖離条件 — 例: `URL → ストアの同期は 1 回きり`
- 複数箇所にまたがる共通ポリシー — 例: 買掛系 3 画面共通の push / replace ポリシー

**B. コードを読んでも「無い」ことが分からないもの**（現行の②③④を維持）

- 担保していない範囲（緑のまま通ってしまう穴）
- 実装と意図的に違う作りにしている理由
- 実行時に協調する相手の責務

あわせて明記する — **「外すと何が壊れるか」自体は残す理由にならない**。壊れ方の説明であっても、型・制御フロー・エラーメッセージ・テストが担保済みなら削る。

### 3. 新削除類型 A-7 — 将来の編集者への牽制

実装の正しさではなく編集の禁止を主張するコメントを、削除類型として追加する。3 つの派生形を実例つきで列挙する。

- **実装順序の牽制** — 「コミットは await の前。後ろに置くと、待っている間に flush された watch が冪等ガードをすり抜ける」。守りたい順序はテストで守る
- **型システムが既に守っているものの牽制** — 「三項の else 落としと違い、mode に値が増えたら Router のメソッド解決で型エラーになる」。型が担保済み
- **直後のエラーメッセージと同内容** — throw の message が同じことを言っている

判定基準は 2 つ。

- 型・制御フロー・エラーメッセージ・テストが既に守っているか → 守っているなら不要
- コードを読む助けになるか、それとも編集の禁止を主張しているだけか → 後者なら不要

### 4. 集約規則の反転

現行の「1 箇所へ集約し、集約先は箇条書きにする。現場の行には 1〜2 行だけ残す（この集約で JSDoc が長くなるのは許容する）」を反転する。

> 同じ説明が複数箇所にあるときは、**まず全部消せないか**を見る。現地に説明がある限りサマリは要らない。集約先を新設して現地にも残す形（＝二重管理）にしない。

集約が許されるのは、現地の説明を**削除して** 1 箇所へ移す場合だけ。検知側 `reviewer-for-comments` の criterion 6「Consolidation」も同様に反転する。

### 5. 分量目安の補正

「通常 1〜3 行 / JSDoc 3〜4 行」の目安は維持しつつ、**上限に収まっていることは残す理由にならない**を追記する。出典メモによれば今回削除された多くは 1〜2 行だった。分量は超過を疑うトリガーであって、収まっていることの保証ではない。

### 6. 「整理を指示された場合」節の新設

`code-implementer` / `test-implementer` に、コメント整理タスクを受けた際のルールを追加する。

- リライトではなく**削除**を第一候補にする。短く言い換えただけの差分は整理とみなさない
- 整理タスク中に**新しいコメントを追加しない**。散在する説明の集約もしない（現地にある説明が正）
- コメント削除がコードの挙動を変えていないことを diff で確認してからコミットする

検証コマンド（出力が空であること）:

```bash
git diff -U0 <path> | grep -E '^[-+]' | grep -vE '^[-+]\s*(//|\*|/\*\*|\*/)'
```

なお「コメント行が全体の 20% を超えたら過剰を疑う」という比率ルールは**採用しない**。エージェントに行数比率を数えさせる実効性が低く、守られないルールは他の規則の重みを薄めるため。

## 過剰削除への防波堤

本改訂は削除方向へ規約を寄せるため、逆側の暴走を明示的に抑える。

- 保護類型 A / B を**削除類型と同一タスク内で**入れる。削除方向だけを先に入れない
- `reviewer-for-comments` の self-review に「保護類型に該当する指摘は severity を下げるのではなく破棄する」という既存規則を維持する
- 既存の保護（AAA コメント / characterization コメント）は変更しない
- 出典メモの「今回残したもの」4 例を、保護類型の具体例としてそのまま採用する

## 検証方針

自動テストが存在しない領域のため、`rg` によるアンカー文字列の存在・不在確認で検証する。

- 旧文言の消滅: 「これを外す・変えると何が壊れるか」「この場所で何が壊れるか」「結論 + 壊れ方」「順序を変えると何が壊れるか」「What breaks if this is removed or changed」が `cbo/` から消えていること
- 新文言の存在: 担保ゲートの 4 語（型・制御フロー・エラーメッセージ・テスト）が生成側 2 ファイルに、A-7 の見出しが検知側に入っていること
- 検知側と生成側の対応: A-7 の判定基準と保護類型 A / B が両側で 1 対 1 に対応していること（言語は異なる）
- フロントマターの健全性: 変更 4 ファイルの `name:` が各 1 件であること
