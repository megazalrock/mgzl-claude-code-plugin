# implementation-plan-creator-lite 設計書

作成日: 2026-08-13

## 背景と課題

`cbo/agents/implementation-plan-creator.md` が生成する実装計画書は 2000 行規模になることがある。原因は計画書の設計思想そのものにある。

- エージェント本文の「想定読者」節が **「実装者は計画書を写経する」** 前提で書かれている
- その前提から派生する規則が本文に多数ある
  - 「どうするかだけ書いて、どう実現するかを示さないステップ — コードを伴うステップにはコードブロックを必須とする」
  - 「テストケース列挙時は最低 1 例の Arrange-Act-Assert 骨格をコード例で示す。複数 describe の雛形は代表ケースで全体構造を見せる」
  - 「計画書のサンプルコードもプロジェクト規約に完全準拠させる（実装者は写経する）」
- 結果として計画書にテストコードの雛形・モック実装・assertion まで書き込まれ、計画書が肥大化する
- エージェント定義自体も 435 行あり、その多くが「計画書に載せるコードの書き方」に関する規則である

計画書が長いほど、作成時・レビュー時・実装時のすべてでトークンを消費する。実装の細部は実装エージェント（`code-implementer` / `test-implementer`）に委ねられるため、計画書がコードを持つ必然性は薄い。

ただし既存エージェントは実運用中であり、いきなり改修するのはリスクが高い。

## ゴール

- コードサンプルを最小化した実装計画書を出力する**新規サブエージェント**を追加する
- `impl:create` スキルから、詳細版（既存）と軽量版（新規）を選択できるようにする
- 既存の `implementation-plan-creator` の挙動は一切変更しない

## 非ゴール

- 既存 `implementation-plan-creator` の改修（本設計のスコープ外。軽量版の運用実績が出た後に別途判断する）
- `code-implementer` / `test-implementer` の改修（後述のとおり不要）
- `impl:execute` の改修（後述のとおり不要）
- レビュアーエージェント本体の改修（呼び出し時のプロンプトで制御する）

## 決定事項

ブレインストーミングで確定した方針。

- **コードの粒度**: 契約のみ。型定義・関数シグネチャ・定数名・API のリクエスト / レスポンス形状はコードで書き、制御フローや関数本体は日本語の指示で表現する
- **テストの粒度**: テストコードは一切書かず、テスト観点（対象 SUT・検証層・ケース一覧・期待挙動）の列挙のみとする
- **選択方法**: `impl:create` のワークフロー内で毎回 AskUserQuestion により選択させる
- **テンプレート**: `document-saver` に軽量版テンプレートを新設する。既存の詳細版テンプレートは変更しない
- **所要時間**: 軽量版では「想定所要時間」フィールドおよび総所要時間の算出を廃止する。規模は難易度で表現する
- **レビュー体制（軽量版）**: 5-A のレビュアー集合を「テスト主目的なら `reviewer-for-test-code`、それ以外は `reviewer-for-design`」とする。`reviewer-for-logic` は計画書内のコードを読んでロジックを検証する役割のため軽量版では外す。5-B（`implementation-plan-reviewer`）は詳細版と共通
- **エージェント名**: `implementation-plan-creator-lite`
- **実装方式**: 既存エージェントをコピーして削り込む独立ファイル方式（共通部の references 化はしない。エージェントは単一ファイル構造であり、実行時 Read による読み飛ばしリスクとトークン増を招くため）

## 変更対象ファイル

- 新規 `cbo/agents/implementation-plan-creator-lite.md` — 軽量版実装計画書を作成するサブエージェント
- 新規 `cbo/skills/document-saver/references/format-implementation-plan-lite.md` — 軽量版計画書のテンプレート
- 変更 `cbo/skills/document-saver/SKILL.md` — 種類リストとテンプレート対応表に軽量版を追加
- 変更 `cbo/skills/impl__create/SKILL.md` — 作成エージェントの選択ステップ追加、レビュアー集合の分岐追加

## 設計詳細

### 1. 新エージェント `implementation-plan-creator-lite`

配置先は `cbo/agents/implementation-plan-creator-lite.md`。既存 `implementation-plan-creator` をベースに構成する。

#### フロントマター

- `name`: `implementation-plan-creator-lite`
- `description`: コードサンプルを排した軽量な実装計画書を作成する旨を記載する。`impl:create` からの明示指定が主用途であることも明記する
- `tools`: 既存 `implementation-plan-creator` と同一（`Agent` を含む。`code-investigator` への委譲を維持するため）
- `model`: `opus`（設計判断の品質を維持するため既存と同じ）
- `color`: `yellow`（既存 `implementation-plan-creator` の `orange` と区別するため）
- `skills`: `document-saver`, `env:show`

#### 本文構成

既存エージェントからの差分で定義する。

**書き換える節**

- `## 想定読者` — 「実装者は写経する」前提を破棄し、以下に差し替える
  - 計画書が実装者に与えるのは **契約・方針・調査済みの事実** であり、コードそのものではない
  - 実装コード・テストコードは実装エージェントが自ら書く。計画書は「何を満たすべきか」を規定し、「どう書くか」は規定しない
  - ただし **後続ステップが依存する契約**（型・シグネチャ・定数名）は計画書でしか伝わらないため、そこだけはコードで正確に書く
  - 「計画書に書かれていないことは実行されない」という原則は維持する。省略してよいのはコードの実体であり、要件・制約・検証条件ではない

**維持する節**（内容は原則そのまま、コード掲載義務の記述のみ差し替え）

- `## プロジェクトルール参照`
- `## あなたの役割`
- `## コードベース調査の委譲`（`code-investigator` への委譲）
- `## ワークフロー` のステップ 1 / 1.5 / 2 / 3 / 3.5 / 4 / 5
  - ステップ 1 のスコープ規模判定、TDD 有効性の検討は維持
  - ステップ 1.5 のファイル構成マップは維持（`impl:execute` の直列 / 並列判定の根拠となるため）
  - ステップ 2 の担当判定（`code-implementer` / `test-implementer`）は維持
  - ステップ 3.5 のセルフレビュー 3 点は維持。特に「型・シンボル整合性」は軽量版では品質の生命線となるため必須のまま残す
  - ステップ 5 の報告形式から「想定総所要時間」の行を削除する
- `## 計画書作成の指針` の以下のサブ節
  - `### ステップ分割と見積もり` — 分割方針（2 時間超の分割・過剰分割の抑制・ベースラインステップ）は維持し、所要時間の加算・係数・内訳算出に関する項目のみ削除する
  - `### ステップの依存関係と並列実行` — `impl:execute` の並列制御の根拠となるため全面維持する
  - `### 検証ステップ設計` — Grep による機械的検証は計画書の中核価値であり維持する。ただし「雛形コードを計画書に直接書く」旨の記述は落とす
  - `### 計画書内の整合性` — 型・シンボルの整合、部分改訂時の同時更新は維持し、工数・テスト件数・雛形コードの検算に関する項目を削除する
  - `### 判断根拠とリスクの明示` — 縮約して維持する
- `## 実装設計の指針` の以下のサブ節（いずれも計画そのものの設計品質に効くため維持する。ただし「サンプルコードに含める」旨の記述は「計画書本文に明記する」へ言い換える）
  - `### 事前調査・実コード確認` — 計画書の記述を実名・実測値で書くための担保であり、コード量とは独立に必要
  - `### 状態管理・リアクティビティ設計`
  - `### TypeScript 型設計`
  - `### エラーハンドリング設計`
  - `### 共通化・YAGNI・スコープ判断`
  - `### その他の設計観点`
- `## 重要な制約`（禁止操作を計画に含めない等）

**削除する節**

- `### テスト計画` の B（モック実装の落とし穴）・C（テストケース設計とコード例）・D（assertion と Arrange）
  - いずれも「計画書に書くテストコードの書き方」の規則であり、テストコードを書かない軽量版では不要
  - これらの知見は `test-implementer` 本体の「コーディング指針 > テストコード」に同等の内容が既に存在するため、失われない
- `### テスト計画` の A（事前確認）は、後述の `### テスト観点の記述形式` へ統合して縮約する
  - 統合して残すのは「テスト観点を決めるために計画段階で確認すべきこと」に限る（既存テストの重複確認、共通 fixture / factory の再利用、検証層の選択、既知バグをテストで温存しない）
  - Vitest / モックライブラリの実装上の落とし穴（`clearMocks` の挙動、`vi.hoisted` の巻き上げ等）は `test-implementer` 側の責務として落とす
- `### コード例・コメントの記述ルール` 節ごと削除（写経前提の規約であるため）
- `### 計画書内の整合性` のうち、工数・テスト件数・雛形コードの整合検算に関する項目
- `### ステップ分割と見積もり` のうち、所要時間の加算・係数・内訳算出に関する項目

**新設する節**

- `### コードを書いてよい範囲`
  - 書いてよい: 型定義・インターフェース・関数シグネチャ・定数名と値・API のリクエスト / レスポンス形状・設定ファイルの差分
  - 書かない: 関数本体・制御フロー・テストコード・モック定義・JSX / template マークアップ
  - 判定基準: 「後続ステップまたは実装者が**その名前と型を正確に知らないと実装できない**もの」だけを書く
  - 契約は `Interfaces` フィールドに集約し、`実装内容` には日本語の指示を書く
- `### テスト観点の記述形式`
  - 各テストステップは以下を列挙する
    - 対象 SUT（ファイルパスとシンボル名）
    - 検証層（composable 単体 / ストア単体 / コンポーネント / 統合）
    - ケース一覧（入力条件 → 期待結果を 1 行 1 件）
    - 網羅する分岐と、意図的に省略する分岐およびその理由
  - テストコード・雛形・モック定義は書かない
  - 「上記のテストを書く」のような無内容な指示は禁止のまま維持する（禁止フレーズ節に残す）
- `### 禁止フレーズ` の差し替え
  - 「コードを伴うステップにはコードブロックを必須とする」を削除し、代わりに「実装内容が日本語で具体的に確定していること（何をどの条件でどう変えるか）」を要求する
  - その他のプレースホルダ禁止（TBD・適宜・必要に応じて等）は維持する
- `### ステップ3.5: セルフレビュー` に 4 点目「コード混入の走査」を追加
  - 計画書内のコードブロックを全件確認し、「コードを書いてよい範囲」に該当しないものが混入していないか点検する

想定行数は 240〜400 行。既存 435 行のうち機械的に削除できるのは「テスト計画 B / C / D」（約 38 行）と「コード例・コメントの記述ルール」（約 20 行）で、残りは各節の縮約による。軽量化の主目的は生成される計画書の縮小であり、エージェント定義の行数削減は副次的な効果である。

### 2. 軽量版テンプレート `format-implementation-plan-lite.md`

配置先は `cbo/skills/document-saver/references/format-implementation-plan-lite.md`。

詳細版 `format-implementation-plan.md` との差分は以下のとおり。

**同一のまま維持する部分**

- ヘッダ（`Goal` / `Architecture` / `Tech Stack`）
- `## Global Constraints`
- `## 実装計画の実行時のルール`（固定テキスト 3 項目）
- `## ファイル構成マップ`
- `## 不明点・確認事項`
- フッタ（作成日時 / 最終更新日 / ブランチ名）

**変更する部分**

- 実装ステップの項目を以下に変更する
  - `**難易度**` / `**担当**` / `**概要**` / `**実装内容**` / `**Files**` / `**Interfaces**` / `**依存関係**` / `**TaskList依存関係**`
  - `**想定所要時間**` を削除する
- テスト実装ステップは `**実装内容**` の代わりに `**テスト観点**` を使う
  - 対象 SUT / 検証層 / ケース一覧 / 網羅と省略の方針
- TDD 採用ステップの書式は RED / GREEN の 2 ステップ構成を維持する
  - RED ステップは `**テスト観点**` と `**RED 確認**`（実行コマンド・期待される失敗）で構成する
  - `**RED 確認**` の記述粒度（失敗の種類 + メッセージに含まれるべき文字列、部分一致レベル）は詳細版と同一の規定を維持する。`test-implementer` の RED 判定 3 分岐がこの粒度に依存しているため
  - GREEN ステップは `**実装内容**` に日本語の指示を書き、`**GREEN 確認**` を維持する
- `## 技術的考慮事項` / `## リスクと対策` は維持する（本文が短いため肥大化要因ではない）

**テンプレート内コメントの方針**

テンプレートの HTML コメントに「コードの実体をここに記載する」という指示が残っていると軽量版の趣旨と矛盾するため、該当箇所を「日本語で具体的な指示を書く。コードは書かない」に置き換える。

**レビュー指摘の修正時（5-A / 5-B の手順 3）**

軽量版を選択している場合、指摘の反映によってコードサンプルを追加してはならない旨を明記する。契約（型・シグネチャ・定数名）の追記は許容する。

**手順 4・6・7・8**

変更しない。

## 既存資産への影響

- `code-implementer` / `test-implementer` — **改修不要**。両エージェントとも「計画書のコードを写経する」旨の記述を持たず、計画書からは「担当ステップの詳細・依存関係・前提条件・期待される成果物」を読み取る設計になっている。`test-implementer` は「SUT のコード構造から対称性・境界・防御分岐を導出する」と規定されており、テスト観点からの自力設計を前提としている
- `impl:execute` — **改修不要**。参照するのはステップのタイトル・詳細・依存関係・難易度であり、所要時間は参照していない
- `implementation-plan-reviewer` — **改修不要**。レビュー基準 10 項目にコード例の掲載要求・所要時間の記載要求は含まれない。基準 3（1 ステップの作業量）は「1〜2 時間で完了できる範囲」を推奨するが、これはステップの内容から評価可能である
- 既存 `implementation-plan-creator` および `format-implementation-plan.md` — **無変更**

## リスクと手当て

- **軽量版で情報が落ちすぎ、実装者が誤った実装をする**
  - 手当て: `Interfaces`（Consumes / Produces）の記載を必須のまま維持し、セルフレビューの「型・シンボル整合性」突合も必須で残す。契約だけはコードで正確に書かせる
- **`reviewer-for-test-code` がテストコードの不在を理由に空転指摘を出す**
  - 手当て: 軽量版でのレビュアー起動時に上記の但し書きをプロンプトへ含める。それでも空転指摘が続く場合は、レビュアー本体への条件分岐追加を別途検討する（本設計のスコープ外）
- **選択肢が増えることによる運用の迷い**
  - 手当て: AskUserQuestion の選択肢に「コードサンプルの有無」を明示し、軽量版を先頭に置く

## 検証方法

- `impl:create` を軽量版で実行し、生成された計画書にコードフェンスが型・シグネチャ以外に含まれないことを確認する
- 生成された計画書の行数が、同等スコープの詳細版と比べて有意に短いことを確認する
- 生成された計画書を `impl:execute` に投入し、ステップ登録（難易度・依存関係の読み取り）が正常に動作することを確認する
- 詳細版を選択した場合に、現行と同一の挙動（`implementation-plan-creator` 起動、5-A の design + logic レビュー）となることを確認する
