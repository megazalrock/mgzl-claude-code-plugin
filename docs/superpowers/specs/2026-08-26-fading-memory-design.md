# fading-memory プラグイン設計書

作成日: 2026-08-26
元素案: `docs/fading-memory/draft-proposal.md`

## 背景と目的

Claude Code 組み込みの memory 機能には忘れる仕組みがなく、記憶が永久に肥大してゆく。
本プラグインは「自動で記憶し、参照されない記憶は薄れて消える」memory 機能を提供する。

組み込み memory とは**併用**する。役割分担は以下の通り。

- 組み込み memory: ユーザーが手入れする厳選された記憶（従来通り）
- fading-memory: セッションから自動抽出され、参照されなければ朽ちる記憶

スコープは**プロジェクト単位**。グローバル共有の記憶は初版では扱わない。

## 用語

- **記憶データ**: 1関心1ファイルで保存されたナレッジ。frontmatter にメタデータを持つ Markdown
- **スコア**: 記憶データが「実際に役立った」と判定された回数
- **有効期限**: frontmatter から計算される派生値。これを過ぎた記憶データは削除される
- **目次**: 記憶データの一覧（INDEX.md）。SessionStart でコンテキストに注入される
- **再構成**: 記憶データの内容が今も正しいかを検証し、更新・削除する処理

## 決定事項と根拠

設計の分岐点で選んだ選択肢と、その理由を記録する。

- **保存形式: 全部 Markdown + frontmatter**
  - 正データは各 .md ファイルに1箇所のみ。目次・state は再生成可能な派生物とし、
    「壊れ方が存在しない」構造にする。index.json や SQLite は二重管理・専用 CLI が
    必要になり、実装をシンプルに保つ方針と衝突するため不採用
- **有効期限: スコア線形式 + 上限 + 直近参照の下限保証（B' 式）**
  - 重要度（スコア）が寿命に反映され、上限により無限延長せず、下限保証により
    現役で使われている記憶が確定死亡日で消えることもない
- **参照検知: LLM 判定に一本化**
  - SessionEnd の抽出処理が「実際に役立った記憶」を判定してスコアを加算する。
    Read フックによる機械検知は、再構成・一覧表示などの目的外アクセスまで
    加算してしまうため不採用。この決定により PostToolUse フックは存在せず、
    スクリプトによるメンテナンス処理がスコアを汚す経路はない。LLM が記憶を
    読む再構成セッションについては、抽出プロンプトの除外指示で加点対象から
    外す（保証ではなく軽減策）
- **記憶データの生成: SessionEnd で直接生成（セッション記録の廃止）**
  - 素案にあった中間生成物「セッション記録」は、保存・変換・掃除の実装が
    増えるだけで役目がないため廃止
- **再構成のトリガー: 手動スキルのみ（初版）**
  - 再構成本体を独立スキルとして実装し、将来「SessionEnd での間隔チェックによる
    自動起動」を数行の追加で足せる構造にする

## プラグイン構成

```
fading-memory/
├── .claude-plugin/plugin.json
├── hooks/
│   ├── hooks.json
│   ├── session-start.ts   # 期限切れ削除 → 目次生成 → コンテキスト注入
│   ├── session-end.ts     # 記憶抽出 + 役立ち判定（headless 呼び出し）
│   └── lib/               # 共有ロジック（frontmatter 解析・期限計算・目次生成・config）
└── skills/
    └── maintain/SKILL.md  # 再構成（手動実行）
```

- スクリプトは TypeScript + bun（リポジトリ規約通り）
- `.claude-plugin/marketplace.json` の `plugins` 配列に fading-memory を追記する
- `plugin.json` に `version` フィールドは追加しない（リポジトリ規約）

## データ配置

`~/.claude/fading-memory/<プロジェクトスラッグ>/` 配下に保存する。

```
memories/<slug>.md   # 記憶データ本体（正データ）
INDEX.md             # 目次（派生物。消しても再生成可能）
state.json           # 最終メンテ日時などの状態（失われても次回メンテが早まるだけで無害）
trash/               # 削除された記憶の退避先
```

- プロジェクトスラッグは組み込み memory と同じ規則
  （プロジェクトの絶対パスのパス区切りを `-` に置換）で導出する
- リポジトリ内に置かない理由: git 差分を汚さず、ユーザーが管理権を持たない
  リポジトリでも動作させるため
- `trash/` は LLM の誤判定による記憶消失への安全網。削除された記憶はまず
  trash/ へ移動し、30日経過後に SessionStart フックが完全削除する。
  復旧は手動（ファイルを memories/ に戻すだけ）

## 記憶データ形式

```markdown
---
title: どのケースで役立つ何の情報かの一行
created: 2026-08-26T10:00:00+09:00
updated: 2026-08-26T10:00:00+09:00
lastReferenced: null
score: 0
permanent: false
related: [other-slug]
---
本文（再利用可能なナレッジ。セッション内の一時的な情報は入れない）
```

- `slug`（ファイル名）は title から抽出 LLM が kebab-case で生成。
  既存と衝突した場合は `-2`, `-3` を付す
- `lastReferenced` は「役立った」と判定された最終日時。未判定なら null
- `permanent: true` は「忘れてはならない記憶」。ユーザーが明示的に指示した
  場合のみ設定する（抽出 LLM が自発的に付けることはない）
- `related` は関連する記憶データの slug の配列

### 有効期限の計算式

有効期限はファイルに**保存しない**。frontmatter から常に計算できる派生値であり、
保存すると二重管理に戻るため。

```
有効期限 = max(
  created + min(基本TTL + score × スコア単価, 上限),
  (lastReferenced ?? created) + 基本TTL
)
permanent: true の場合は Infinity
```

- 第1項（スコア線形 + 上限）: 重要度が寿命を延ばすが、上限で頭打ち
- 第2項（下限保証）: 直近で役立った記憶は、少なくとも基本TTL の間は消えない

定数は `hooks/lib/config.ts` に一箇所集約する。初期値:

- 基本TTL: 30日
- スコア単価: 7日（スコア1につき7日延長）
- 上限: 120日（created からの最大延長。スコア約13で頭打ち）
- trash 保持期間: 30日
- headless 呼び出しモデル: sonnet

## 動作フロー

### SessionStart フック（純スクリプト・ミリ秒級）

1. `trash/` 内の30日超過ファイルを完全削除する
2. `memories/` を走査し、有効期限切れのファイルを `trash/` へ移動する
3. 全 frontmatter から INDEX.md を再生成する
   - 並び順: permanent が先頭、以降は有効期限の降順（= 重要度順）
   - 各行: `- [title](memories/<slug>.md)` の形式
4. INDEX.md の内容を `additionalContext` としてコンテキストに注入する

Claude は注入された目次を見て、関連しそうな記憶データだけを Read して利用する。
この Read 自体はスコアに影響しない（スコア加算は SessionEnd の LLM 判定のみ）。

### SessionEnd フック

1. フック本体はデタッチしたバックグラウンドプロセスを起動して即 exit 0 する
   （セッション終了をブロックしない）。プロセスの stdout/stderr はログファイルへ
2. バックグラウンドプロセスは軽量モデルの headless 呼び出し
   （`claude -p --model sonnet`）を1回行う。入力はトランスクリプトと現在の目次。
   出力は以下の JSON:
   - `newMemories[]`: 新規記憶データ（title / 本文 / related）
   - `updatedMemories[]`: 既存記憶データの更新（slug / 本文 / related）
   - `usefulMemorySlugs[]`: このセッションで実際に読まれ、かつ作業に役立った
     既存記憶データの slug
3. スクリプトが結果を反映する:
   - newMemories → slug を生成して .md を書き出す（created / updated は現在時刻）
   - updatedMemories → 本文を差し替え、updated を更新する
     （更新だけでは score / lastReferenced は変動させない）
   - usefulMemorySlugs → 各記憶データの score を +1、lastReferenced を現在時刻に更新する
4. 出力が JSON として不正な場合は、一切反映せずログに記録して終了する

抽出の基準: セッションを跨いで再利用可能なナレッジのみ。セッション内の
一時的な作業情報は記憶しない。

### `/fading-memory:maintain` スキル（再構成・手動実行）

1. 有効期限の遠いもの（= 重要度の高いもの）から順に、記憶データの内容を
   コードベース等の現状と突き合わせて検証する
2. 判定と処置:
   - 内容が正 → 何もしない
   - 内容が偽 → `trash/` へ移動し、目次からも消す（次回の目次再生成で自動反映）
   - 部分的に正 → 本文を修正し、updated を更新する
   - permanent な記憶が偽と判定された場合 → 削除せず、ユーザーに報告する
3. 再構成による読み取り・更新でスコアと lastReferenced は変動させない
4. 完了後、INDEX.md を再生成し、state.json の最終メンテ日時を更新する

## エラーハンドリング

- フックは絶対にセッションを壊さない。処理全体を try/catch で包み、
  失敗はデータディレクトリ内の `error.log` に記録して exit 0 する
- frontmatter が解析できないファイルは処理対象から除外してログに残す
  （削除はしない）
- headless 呼び出しの失敗・タイムアウト・不正な出力は「そのセッションの記憶は
  作られない」だけで、既存データには影響しない

## テスト

- `bun test` によるユニットテスト: 有効期限計算・frontmatter 解析・目次生成・
  slug 生成を純関数として切り出してテストする
- フック結線と headless 呼び出しは手動 E2E で確認する
  （テスト用プロジェクトで1セッション回し、記憶の生成 → 注入 → 加点 → 失効を追う）

## 初版でやらないこと（将来拡張）

- グローバル記憶（全プロジェクト共有の層）
- 組み込み memory との重複排除
- 再構成の自動トリガー（SessionEnd で state.json の最終メンテ日時を見て
  7日以上経過していたら headless で maintain 相当を起動する。
  再構成本体には手を入れず、SessionEnd フックへの数行の追加で実現できる）
- trash からの復元支援機能（初版は手動でファイルを戻す）
- SessionEnd の reason（clear / logout 等）やトランスクリプト規模による
  抽出スキップ（現状は /clear のたびに headless 抽出が走り、コストが掛かる）
- malformed（frontmatter が解析できない）ファイルの回収経路
  （現状は error.log に記録されるのみで、削除はユーザーの手作業）
