## 総評

- **審査スコアは 3 タスク × 3 軸すべてで opus ≥ sonnet、3 タスクとも opus の明確な勝利**。規模（小・中・大）・種別（UI 改修・perf ロジック・画面横断改修）を問わず一貫した
- **客観ゲート（lint / 型 / 既存テスト）は 6 実行とも同等の全 pass**。つまり品質差はすべて「ゲートで検出できない軸」— 要件解釈の踏み外し（T1）、ライフサイクル設計の穴（T2）、構造的でない表層対応（T3）— に現れた。ゲート green はモデル間品質差の判定材料にならない、という点自体が本ベンチの重要な副産物
- コスト通念に反し、**トークン消費は opus が全タスクで sonnet を下回った**（sonnet は試行錯誤・広い読み込みでトークンを多く使う傾向）。実時間のみ opus が約 16% 長い
- 報告品質は両者とも報告形式遵守・test-implementer 引き継ぎ明記を達成。opus はスコープ外発見の別 PR 提案・ブラウザ確認依頼など報告の解像度が高い一方、T3 で既存型エラーの列挙に漏れ（申告 5 件 / ベースライン実測 8 件。新規 0 という結論は正しい）。sonnet は既存エラーの列挙が正確
- リーク統制: 指示文は人間レビュー済み・git 履歴参照禁止を明示。sonnet が T3 で `git show HEAD:<path>`（チェックアウト中コミット自身の参照）を使用したが、正解実装は HEAD の子孫にのみ存在するため実害なし（字義違反として記録）

## 推奨アクション

**「opus へ切替」を推奨**

切替判断の目安への当てはめ:
- 審査スコア優位: 3 タスク中 3 タスクで opus 優位（目安の 2 タスク以上を満たす）
- 客観ゲート: 同等（両者とも全 pass）
- コスト増: トークンはむしろ 15% 減、時間のみ +16%（3 タスクで +10 分）— 許容範囲

補足: 単価差（opus のトークン単価 > sonnet）を考慮しても、消費トークン自体が少ないため金額差は単価比ほど開かない。sonnet 維持の根拠となる「品質ほぼ同等」は今回の結果からは支持されない

## パイロットの限界

- 各条件 1 回実行のため、モデル内ばらつきとモデル間差を統計的に区別できない。ただし今回は 3 タスクすべて同方向かつ大差（各軸 2 点差）であり、「僅差の場合のみ追加実行」ルールには該当しない
- 審査員は fable 1 名 × 1 回。スコアが 5 / 3 に二極化しており、絶対値より相対順位（opus 優位）に信頼を置くべき
- 客観ゲートの回帰テストは既存テストの範囲のみ。T2 の交差（IntersectionObserver）挙動には既存テストが存在せず、sonnet のバグ経路指摘は審査員のコードレビューベース（ユーザー目視で妥当性確認済み）
- ブラウザでの視覚確認は未実施。opus の T2（スクロールコンテナ移設）・T3（高さ再設計）は視覚退行リスクが残る変更であり、実採用時は画面確認が前提
- リプレイした 3 PR はすべてスケジュールドメイン。他ドメイン（Order 等）への一般化は未検証
